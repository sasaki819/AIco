# 05. ブランチ・並行作業方針

## 概要

成果物と管理記録の食い違いや、複数作業による共有ファイルの競合を防ぐための方針を示す。
本章では以下を定める。

* **ブランチ戦略の基本形**：3層構成と統合ブランチ1本の不変条件
* **ブランチごとの更新責務**：統合ブランチと作業ブランチの更新範囲
* **並行作業時の衝突防止**：事前の重なり確認と一覧の範囲
* **並列実行方式との境界**：Git worktree等の導入先方針との切り分け

## 1. ブランチ戦略の基本形

AIcoのブランチ戦略は、**`main` ← `develop`（統合ブランチ）← `feature/*`（作業ブランチ）** の3層を基本形とする。
これは一般的なGit Flowから `release` や `hotfix` を省いた簡易版Git Flowの構成に相当する。

* **`main`**：リリース済みまたは安定版を保持するブランチ。
* **統合ブランチ（基本は `develop`）**：全体の共有情報、起票、および各作業ブランチの成果を統合するブランチ。
* **作業ブランチ（基本は `feature/*`）**：個別チケットの成果物と作業記録を更新するブランチ。

AIcoの前提として、管理情報を集約する**統合ブランチは常に1本**とする。
導入先が `main` を直接統合先とする運用（GitHub Flowなど）を採用している場合でも読み替えられるよう、AIcoの方針・仕様では統合先を「統合ブランチ」と呼ぶ。
チケット起票時に導入先規約に従って作業ブランチ名を決定し、チケット対応を開始する際に該当の作業ブランチへ切り替えること。

`release/*` や `hotfix/*` を含むフルGit Flowの専用フローは、統合先の二重化や逆マージ時の管理情報競合を招くため、AIcoでは規定しない（サポート対象外とする）。
導入先がリリース運用としてこれらのブランチを併用する場合でも、管理情報の起票・ダッシュボードおよび一覧の更新は常に1本の統合ブランチ側で行うこと。

## 2. ブランチごとの更新責務

複数の作業が共有ファイルを同時に書き換えて競合することを防ぐため、ブランチごとの更新範囲を以下のとおり明確に分ける。

| ブランチ | 更新するもの | 更新してはならないもの |
| :--- | :--- | :--- |
| **統合ブランチ** | 議事録・ADR・Runbookなどの共有情報、チケット起票、ダッシュボード・各区分の一覧再生成 | 個別チケットの実装途中コード |
| **作業ブランチ** | 対象チケットの成果物、対象チケット配下の作業・レビュー記録、チケット内一覧、完了時のチケット状態更新 | 管理ルートダッシュボード・各区分一覧、他チケットの記録、全体の共有情報 |

個別チケットの成果物と作業記録は同じ作業ブランチで一体管理し、完了時に作業ブランチ側で対象チケットの状態を完了（`done` または `cancelled`）へ更新してから、まとめて統合ブランチへ取り込むこと。
統合後は統合ブランチ側でダッシュボードおよび各区分の一覧を再生成する。

## 3. 並行作業時の衝突防止

複数チケットを並行して進める際は、ファイル競合と仕様矛盾を防ぐため以下の3点を守ること。

* **事前の重なり確認**：並行着手する前に、変更予定ファイルと影響する仕様を照合する。
* **共有対象の調整**：共有ファイルの編集が重なる場合は担当または反映順序を決め、一方の仕様判断が他方を左右する場合は先に判断を共有する。
* **一覧の範囲の認識**：統合ブランチのダッシュボード・一覧には未統合の進捗は反映されないため、作業中の最新状況は各作業ブランチのチケット記録で確認する。

## 4. 並列実行方式（Git worktreeなど）との境界

Git worktreeを用いたマルチエージェント並列開発などの実行方式は、AIcoの本質とは切り離して扱う。
AIcoの方針・仕様としてworktreeの構成基準や運用手順は定めないこと。
ただし、チケット対応を開始して作業ブランチへ切り替える際に、導入先プロジェクトでworktree等に関する方針が規定されている場合は、その方針に従って作業環境を準備すること。
