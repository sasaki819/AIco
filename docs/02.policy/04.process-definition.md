# 04. プロセス定義

## 概要

ユーザーが日々の協業の進め方を全体像として理解できるようにし、後続の仕様・スキル設計の基準とする。
本章では以下を定める。

* **相談・構想（議事録）**：テーマ未定の段階からの進め方とチケット移行
* **チケット対応**：DoR・判断を戻す条件・独立レビュー・DoDの流れ
* **定常作業（Runbook）**：手順書に基づく実施と別作業への引き継ぎ
* **中断と再開の記録**：チケットとRunbookに共通する再開用記録
* **知見の蓄積**：設計判断のADR化と繰り返し手順の資産化

各工程の具体的なスキル一覧や詳細な操作手順は、本章の方針に従い仕様で導出する。

## 1. チケット起票前の相談・構想（議事録）

仕事はテーマ名や受け入れ基準（AC）が定まっていない相談段階から始めてよい。
議事録を相談の入口とし、発端・合意したことと理由・次の判断に必要な未決事項を残すこと。

* **事実の先行確認**：AIは相談の範囲で自ら確認できる事実を先に調べ、確認できた事実と仮説を区別して示す。
* **選択肢と推奨案の提示**：人の意図や優先順位で進め方が変わる点は、選択肢と推奨案および次に取る行動を具体的に提示する。
* **相談での完結と保留**：相談のみで解決した場合や見送り・保留とする場合は、結論と理由を議事録に残して区切る。
* **チケットへの移行**：次に任せたい仕事と期待する成果を説明できればチケットを起票し、議事録とチケットを相互参照する。

議論の途中で複数の仕事に関わる重要な設計判断が決まった場合は、その時点でADRへ記録し、議事録から参照すること。

## 2. チケット対応

チケットは `index.md` を作業の入口とし、着手合意・実行・独立レビュー・完了確認の順に進める。

### 2.1. 起票時のDoR確認と着手の合意

チケット起票時は、共通の準備完了の定義（DoR）に照らして以下の3点を確認し、作業の入口へ記録すること。

| 合意すること | 確認する問い |
| :--- | :--- |
| **目的** | この仕事で何を解決したいか |
| **今回のAC** | 何を確認できれば目的を達成したといえるか |
| **任せる範囲** | 調査・変更・反映のどこまでをAIへ委ねるか |

未決事項が残っていても起票してよいが、今回の着手を妨げる未決事項は明示して記録すること。
着手時は起票時の結果を引き継ぎ、未決だった点や範囲が変わった点だけを再確認する。
依頼文や合意済み仕様で明確な項目は、その参照で代替してもよい。

### 2.2. 対応中の進行と人へ判断を戻す条件

AIは合意した範囲とACに沿って調査・実装・検証を進め、各段階の区切りで現在地に応じた次の行動や選択肢を提示すること。
調査では問いへの回答・根拠・未確認範囲を、実装や修正では合意した振る舞い・変更箇所・検証結果を辿れるように記録する。
以下の4条件に当たる場合は、該当作業を止めて人へ判断を求めること。

| 判断を戻す条件 | 具体例 |
| :--- | :--- |
| **利用者から見た振る舞いを新たに決める** | 重複結果を統合すると個別の履歴表示が消える |
| **目的・AC・対象範囲が変わる** | 画面内修正の想定が共通APIの仕様変更を伴う |
| **既存仕様・ADRまたは既知の別作業と矛盾・競合が生じた** | 統合時の競合、既存ADRや共有済みの他チケット方針との食い違い |
| **実行に個別の承認を要する** | 本番反映やデータ削除が必要になる |

他作業との矛盾・競合の検知にあたり、作業ブランチ側から他の作業ブランチを全件調査することは求めない。
着手前の確認、共有済みの前提、または統合時の競合などにより検知した事象を対象とする。
判断を求める際は、判明した事実・選択肢ごとの影響・AIの推奨案を提示し、判断に依存しない作業は合意範囲内で継続してもよい。

### 2.3. 独立レビューと指摘管理

実装時の思い込みや自己追認を防ぐため、品質検証とレビューは以下の原則で行うこと。

* **コンテキストの分離**：AIによるレビューは、実装を担当したセッションとは独立したコンテキストで実施する。
* **人間の選別**：AIが挙げた指摘の採否（対応するか見送るか）は必ず人が判断し、AIは独断で採否を決定してはならない。
* **1件1ファイル管理**：指摘は1件1ファイルで記録し、発見・採否判断・修正・再確認の経緯を追跡できるようにする。
* **検証範囲の明示**：検証や再レビューの報告では、確認した実行環境と未確認事項を区別して明記する。

### 2.4. 完了時のDoD確認とクローズ

完了時は共通の完了の定義（DoD）に従い、今回のACごとに結果と根拠を実物と照合して確認すること。
必要な記録および該当するADRが作業の入口から辿れることもあわせて確認する。

* **親子チケットのクローズ**：子チケットは自身のACで閉じ、親チケットは子の結果を参照して親自身のACを確認してから閉じる。
* **未検証項目の扱い**：ACに未検証の項目が残る場合は、完了前に「その状態を受け入れて完了とするか、検証を引き継ぐか」を人へ確認すること。
  未検証項目と人の判断結果、引き継ぐ場合は追跡先リンクを作業の入口へ記録する。

## 3. 定常作業（Runbook）

定例の作業は該当するRunbookから直接開始し、使用した手順と実行結果を実施記録へ残すこと。
手順が求める結果を確認できれば、その回の作業は実施記録で完結する。

| 実施中に分かったこと | 次の進め方 |
| :--- | :--- |
| **傾向は見えるが課題や施策が曖昧** | 実施記録を根拠に相談を始め、議事録へつなげる |
| **課題と任せたい仕事が具体的** | 実施記録からチケットを起票し、相互参照する |

別作業へ引き継いだ場合は、実施記録と引き継ぎ先を相互参照できるようにする。
手順の完了条件を検証できなかった場合は、チケット対応と同様に人へ判断を求め、判断結果と追跡先を実施記録へ残すこと。

## 4. 中断と再開の記録（チケット・Runbook共通）

チケット対応とRunbook実施のいずれにおいても、セッション中断後に別セッションから正確に再開できるよう、作業記録に以下の4要素を残すこと。

* **完了済み事項**：何が終わっており、どこまで検証済みか。
* **未完了事項**：合意範囲または手順のうち何が残っているか。
* **次に行うこと**：再開時に最初に取るべき具体的な行動。
* **判断理由**：途中の選択でなぜその方式を採ったか。

再開する担当は、入口の要約だけを鵜呑みにせず、完了済み事項・未完了事項・未対応の指摘・実際のファイル差分を照合してから作業を再開すること。

## 5. 知見の蓄積（共通）

議事録・チケット・Runbookのいずれの活動であっても、再利用価値のある知見が得られた場合は作業ログへ埋もれさせず、性質に応じて切り出すこと。

* **設計判断の切り出し**：複数の仕事に影響する重要な決定は、背景・選択肢・採用理由・却下案をADRへ記録する。
* **手順の資産化**：今後も繰り返し実施する操作や工程は、Runbookやスキルへ反映する。
