# 08. 導入・カスタマイズ・更新方針

## 概要

導入先プロジェクトの既存ファイルとの衝突や上書きを避け、既存の構成を崩さずにAIcoを導入できるようにする。
また、導入後に固有設定や作業記録を守りながら、新しい版へ安全に更新し続けるための方針を示す。
本章では以下を定める。

* **既存プロジェクトへの安全な導入**：既存構成を尊重した最小前提での導入
* **領域の分離**：AIco由来領域とプロジェクト固有・作業記録領域の区別
* **バージョン管理と移行**：SemVer運用と厳密な移行手順・スクリプトの提供
* **ドッグフーディング**：配布物と運営領域の分離およびリリース前検証

## 1. 既存プロジェクトへの安全な導入

AIcoは、導入先プロジェクトの既存ファイルやディレクトリ構成を壊さずに適用できること。

* **既存構成の尊重**：管理資材は専用の管理ルートや規定のツール設定へ集約し、導入先のソースコード配置やシステム設計書の構造を制約しない。
* **前提ツールの最小化**：基本運用はMarkdown・Git・Python（`uv`）のみで完結させ、特定の外部サービスや専用UIの導入を前提にしない。
* **導入時の動作確認**：初回導入時は `doctor` を実行し、必要な実行環境および対象AIツールでの規約・スキル読み込みを確認すること。

## 2. AIco由来領域とプロジェクト固有領域の分離

将来のアップデートで固有設定や作業記録を失わないよう、所有範囲を明確に分離すること。

| 領域 | 所有者 | 主な対象 | 編集・更新の原則 |
| :--- | :--- | :--- | :--- |
| **AIco由来領域** | AIco | 共通規約、スキル、テンプレート、共有スクリプト | 導入先で直接改造せず、アップデート手順で差し替える |
| **プロジェクト固有領域** | 導入先 | 固有のビルド・開発規約、固有ツール、モデル割り当て | AIcoの更新で上書きしない |
| **作業記録領域** | 導入先 | 議事録、ADR、チケット、Runbook、生成済み一覧 | 配布物の雛形で上書きしてはならない |

`AGENTS.md` や一覧の `index.md` のように1ファイル内で両領域が共存する場合は、開始・終了マーカーで更新範囲を明確に区切ること。
AIcoの標準規約を導入先に合わせて上書きしたい場合は、AIco由来領域を直接書き換えず、プロジェクト固有の規約領域へ変更内容と理由を記載する。

## 3. バージョン管理と厳密なマイグレーション

AIcoの版はセマンティックバージョニング（SemVer）で管理し、変更履歴（`CHANGELOG.md`）には変更内容に加えて変更意図と移行の要否を明記する。

* **厳密な手順とスクリプトの提供**：既存の管理情報や設定へ影響する仕様変更を含むリリースでは、導入先ごとの場当たり的な判断に頼らず移行できるよう、厳密な移行手順と検証済みのマイグレーションスクリプトをAIco側から提供すること。
* **手順に基づく適用と検証**：アップデートは提供された手順とスクリプトに沿って実施し、`--dry-run` による影響確認とバックアップ可能な状態を確認したうえで適用する。
  適用後は、版の一致・設定の過不足・リンク参照・一覧の再生成・`doctor` の結果を確認すること。
* **想定外への対応**：手順やスクリプトの実行中に想定外の問題が生じた場合は、処理を止めて状況を確認し、人とAIが協力して復旧方針を判断する。

## 4. リポジトリ構成とドッグフーディング

AIco自身の開発においても、配布物の品質と移行手順の妥当性を継続的に検証する体制を採る。

* **配布物と運営領域の分離**：AIco本体のリポジトリでは、導入先へ展開する配布テンプレートと、AIco本体開発のための運営領域を分離して管理する。
* **ドッグフーディングによる検証**：新しい版をリリースする前に、AIco本体自身の運営領域へ更新手順とマイグレーションスクリプトを適用し、問題がないことを確認すること。
* **知見の還元**：導入先での運用を通じて得られた汎用的な改善点はAIco本体へ取り込み、次の版として継続的に展開する。
