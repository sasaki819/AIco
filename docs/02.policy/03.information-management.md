# 03. 情報管理方針

## 概要

AIco導入先で「どの情報がどこにあり、どう維持されるか」を全体像として把握できるようにし、仕様設計の基準とする。
本章では以下を定める。

* **管理情報の分離と4区分**：開発成果物との分離および4種の管理フォルダ
* **細分化と命名規則**：長大ファイルの部分更新を避ける定型構成
* **状態管理と移動の抑制**：属性更新による管理とアーカイブ自動化
* **属性・本文・一覧の分担**：frontmatter・本文・ダッシュボードの役割
* **文書品質の規約**：Markdown作成スキルの独立導入

詳細なディレクトリ名やfrontmatterキー一覧は仕様で定める。

## 1. 開発成果物と管理情報の分離

開発対象システムの設計書やソースコードなどの開発成果物と、プロジェクト管理情報の置き場所は明確に分けること。
管理情報はプロジェクトルートの専用管理ルート（基本は `management/`）配下に集約し、Markdown形式でGit管理する。
管理情報の中では開発対象システムの仕様書本体を重複管理せず、必要に応じて参照リンクで結ぶこと。

## 2. 管理する4種の情報

管理ルート配下は、情報の性質に応じて以下の4つのサブフォルダに分けて管理する。

| 管理情報 | 配置先の基本形 | 役割と扱い |
| :--- | :--- | :--- |
| **議事録** | `management/01.discussions/` | 相談・構想の経緯と結論を残す。相談完結や保留の理由もここに記録する |
| **ADR** | `management/02.adr/` | 複数作業に関わる重要な設計判断の背景・選択肢・採用理由・却下案を記録する |
| **チケット** | `management/03.tickets/` | ゴールのある作業を一律に管理する。管理情報の中心とする |
| **Runbook** | `management/04.runbooks/` | 繰り返し実施する定常作業の手順書と、各回の実施記録を管理する |

課題・タスク・調査・機能開発といったゴールのある作業は、種別を分けず一律「チケット」として扱う。
大きな施策を分割して親子チケットを使う場合も、別種別や別構造は作らず、同一構造のまま親子リンクで関連付けること。

## 3. 細分化された定型構成と命名規則

AIが長大な単一ファイルの一部を位置特定して参照・更新する動作は、誤編集やトークン浪費の原因になるため避けること。
役割や記録単位ごとに細かく分割された定型ファイル構成を標準とする。

* **単一記録の命名**：議事録やADRなど単一ファイルで完結する記録は `<日時>-<種類>-<slug>.md` とする。
* **フォルダ単位の命名**：チケットのように付随ファイルが発生する記録は `<日時>-<種類>-<slug>/index.md` を入口とし、配下に定型ファイル群を置く。
* **1件1ファイルの維持**：レビュー指摘のように個別の状態遷移や対応経緯を持つ記録は、1件1ファイルで管理する。
* **固定名の利用**：`index.md`・`README.md`・コンテキストファイル・設定ファイルは役割に応じた固定名とする。
* **規模による構造分岐の禁止**：案件の大小によってテンプレートやファイル構成を分岐させず、一様な構成を維持すること。

`slug` には一覧から内容を識別できる短い名前を付ける。
日時の具体的な書式と名前重複の回避規則は仕様で定める。

## 4. 状態管理と移動の抑制

作成した記録は、状態が変わるたびにフォルダ移動してはならない。
ファイルの場所を固定したまま状態属性と一覧表示を更新することで、参照切れと無用なGit差分を防ぐ。

* **完了済み情報の扱い**：完了した記録も元の場所または参照可能な状態を保ち、一覧上で進行中と分けて表示する。
* **アーカイブの条件**：参照頻度の低い古い情報のみ `archived` フォルダへ移動する。
* **移動の自動化**：アーカイブ移動は手作業で行わず、移動対象へのリンク更新を含めてスクリプトで実行すること。

## 5. 属性・本文・一覧の役割分担

機械的な集計と人間の可読性を両立させるため、属性・本文・一覧の役割を以下のように分ける。

| 要素 | 記載する内容 | 更新のしかた |
| :--- | :--- | :--- |
| **属性（frontmatter）** | 状態、日時、作業ブランチ名、関連先など機械処理する情報 | 規則に従い記録・更新する |
| **本文** | 概要、判断理由、作業内容、検証結果など意味のある記述 | 冒頭の概要だけで把握でき、詳細は後ろに置く |
| **一覧（`index.md`）** | 各記録の概要・状態・リンクの一覧 | スクリプトで生成し、手書き領域と明確に分離する |

全体のチケット一覧（ダッシュボード）は、**`active` / `closed` の状態と作業ブランチ名**を表示する簡潔な構成にとどめること。
個別チケットの詳細な進捗や残件は、全体一覧へ転記せず各チケット配下の記録で管理する。

## 6. 文書品質の規約（Markdown作成スキル）

AIが作成・更新する管理記録の読みやすさと構造を揃えるため、Markdown文書作成ルールを独立スキルとして導入すること。
議事録・ADR・チケット記録・Runbookなどの作成および編集時には、このスキルを適用して構成・文体・表記を統一する。
