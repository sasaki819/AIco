# 07. スクリプト運用方針

## 概要

OS間の二重実装による保守負荷をなくし、AIと人が同じ仕組みを安全に利用できる機械処理の運用方針を示す。  
本章では以下を定める。

* **スクリプト化の境界と言語統一**：Python 3.11以上と `uv run` への一元化
* **依存分離と配置**：導入先環境と干渉しない構成と集約配置
* **AIと人の呼び出し方**：AIの直接実行と人用の共通入口
* **安全性と耐障害性**：終了コード、原子的更新、秘密情報の保護
* **テストと環境確認**：開発側テストと導入先向け `doctor`

個別のスクリプト一覧や引数仕様は仕様書で定める。

## 1. スクリプト化の境界とPython・`uv`一元化

文脈に応じた意味の判断や文章化はAIに任せ、決まった規則で確実に反復すべき検査・採番・一覧生成・同期・移行をスクリプト化すること。  
特に多数ファイルを横断する処理はスクリプト化し、トークン消費と確認漏れを抑える。  
一方で保守コストも踏まえ、単純な編集まで過剰にスクリプト化しないこと。

* **実装言語の統一**：WindowsとLinuxで処理を共用するため、実装はPython 3.11以上へ統一する。  
  BAT・bash・PowerShellで同じ機能を別々に実装してはならない。
* **起動方法と依存の限定**：実行は原則として `uv run` を用い、Pythonや依存関係の準備を委ねる。  
  ただしuvへの依存は起動方法にとどめ、必要なPython環境があればPython単体でも実行できるようにする。
* **初期スコープの限定**：PR・MRの自動作成など外部サービスの認証管理やAPI保守が重い機能は、初期スコープから外す。

## 2. 導入先環境との依存分離と配置

AIcoのスクリプトは、導入先プロジェクトの開発言語や仮想環境と干渉しないよう分離して配置する。

* **標準ライブラリ原則とPEP 723**：原則として標準ライブラリのみを使用し、全スクリプト冒頭にPEP 723形式でPythonの版と依存関係を宣言すること。  
  依存がない場合も宣言し、導入先プロジェクトの環境を使わずに実行する。
* **外部パッケージの例外扱い**：外部パッケージを採用する場合は、標準ライブラリで代替しない理由を記録する。
* **導入先ルートへの非配置**：AIco用の `pyproject.toml`・`uv.lock`・`.venv` を導入先プロジェクトのルートに置かないこと。
* **1か所への集約**：スクリプトは管理ルート配下の `scripts/` に1機能1ファイルで集約し、複数機能で共有する処理は `_lib/` へ置く。  
  スキルフォルダ内へスクリプトを分散配置してはならず、スクリプト同士の直接読み込みも避ける。
* **導入先固有ツールの分離**：導入先固有のツールは管理ルートの外に置き、AIcoの更新対象から分離する。

## 3. AIと人の呼び出し方の分離

AIと人が同じスクリプト実体を使いつつ、それぞれの利用形態に適した入口を用意する。

| 利用者 | 呼び出し経路 | 振る舞いの方針 |
| :--- | :--- | :--- |
| **AI** | スキルから `uv run <管理ルート>/scripts/<機能名>.py <引数>` を直接実行 | 対話待ちにせず、必要な値をすべて引数で受け取る |
| **人** | `tools/aico.bat`（Windows）または `tools/aico.sh`（Linux）経由で実行 | 起動・引数転送・終了コード伝達のみを担い、一覧表示と対話案内は `_launcher.py` に集約する |

人用の入口は、引数なしで端末から起動すると一覧から機能を選び、使い方を確認して実行できるようにする。  
端末に接続されていない環境では入力待ちにせず、uvがない場合は利用可能なPython環境で直接起動できるようにする。

## 4. 実行結果・安全性・耐障害性の規約

スクリプトの失敗や途中停止が作業記録を破壊しないよう、入出力と失敗時の振る舞いを揃えること。

* **変更確認モード**：既定で書き込みを行い、`--dry-run` で変更予定のみを確認できるようにする。
* **終了コードの統一**：成功を `0`、検査・処理の失敗を `1`、引数の誤りを `2` とする。  
  uvやPythonの起動失敗はスクリプトの失敗と区別して原因を確認する。
* **出力と文字コード**：結果・警告・エラーを明確に分け、出力順とUTF-8文字コードを揃える。
* **検査回避の禁止**：スクリプトの検査で停止した処理を、AIが手作業で代行して回避してはならない。
* **原子的更新とべき等性**：完成した内容を検証してから置き換えることで途中停止時の破損を防ぎ、同一入力での再実行で不要な差分を増やさないこと。
* **破壊操作と秘密情報の保護**：自動コミット・自動pushは行わず、削除や上書きには事前検査と復旧手段を定める。  
  秘密情報を引数・出力・ログに含めてはならない。

## 5. テストと導入先での環境確認

開発側での自動検証と、導入先での簡易診断を組み合わせて動作を保証する。

* **開発側テストの分離**：テストコードは配布物の外に置き、共通処理とコマンドとしての動作を検証する。  
  WindowsとLinuxの双方で、空白・日本語パス、引数転送、終了コード、uvなしの起動を確認し、未確認環境はリリース時に明記すること。
* **導入先向け `doctor`**：導入先には標準ライブラリのみで起動できる `doctor` を配布する。  
  必要なツール・設定・文字コード・同期状態を確認し、不足があれば対処方法を案内できるようにする。
