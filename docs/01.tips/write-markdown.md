# write-markdown

## 概要

Markdown文書を作成する際に、読み手の視覚的・認知的負荷を下げ、必要な箇所を拾い読みできるように書く。  
全体の構成を決めてから、文と段落を整える。  
最後に文末表現と装飾を確認する。

## 1. 全体設計と重複の削減

* **冒頭の1〜2文**で、文書や章のテーマ・結論と、対象読者・ゴールを明示する。
* **全体像**を見出し（`#`、`##`、`###`）と導入文で示す。  
  要素の数などを先に示し、概要 → 要素 → 詳細の順に掘り下げる。
* **共通の前提**（条件・時期・主語）は見出し・導入文・表の列名にまとめ、配下の文やセルでの反復を省く。  
  直前の見出しや導入文に明記していない前提は省略しない。  
  警告や注意事項は、単独で読んでも伝わる1文にする。

## 2. 文・段落・箇条書き

* **1文1義・1文1行**を守り、関連する2〜3文を1段落にまとめる。  
  GitHub・GitLab 等の表示で文が連結されないよう、段落内や箇条書き継続行で改行する行末には半角スペース2個を付ける。  
  空行は段落の区切りに入れる。  
  因果や対比は「したがって」「ただし」「一方で」などの接続詞で示す。
* **並列要素が3項目以上**あれば、「以下の〜」で導入し、`**ラベル**：説明` を基本に箇条書きにする。  
  ネストは2階層までとし、3階層目以降は `###` などの見出しに切り出す。
* **結論や主要な行動**を先に書き、理由・条件・補足は文末の括弧 `（）`に置く。  
  文・節を補う括弧は1文に1つまで、長さは20文字以内を目安とする。  
  短い言い換えや英語併記は複数可とし、長い補足は別文か注釈（`※`）に分ける。
* **主語と述語**を近づけるため、長い修飾節を文頭に移すか、「〇〇については、〜」と主題を先に示す。  
  「〜ないこともない」などの二重否定は肯定形に直す。

## 3. 文体と文末表現

### 3.1. 文書種別で文体を選ぶ

| 文書種別 | 地の文 | 混在ルール |
| :--- | :--- | :--- |
| 仕様書・設計書・規約・ナレッジ・手順書 | 常体（だ・である調） | 地の文は常体で統一する |
| 案内文書・解説書・マニュアル・FAQ | 敬体（です・ます調） | 表・箇条書き内のみ常体も可 |

### 3.2. 要求の強さに応じて文末を固定する

| 区分 | 文末表現 |
| :--- | :--- |
| 必須（MUST） | 〜すること / 〜ねばならない / 〜とする |
| 禁止（MUST NOT） | 〜してはならない / 〜を禁止する / 〜しないこと |
| 推奨（SHOULD） | 〜を推奨する / 〜が望ましい |
| 任意（MAY） | 〜してもよい / 〜が可能である |

### 3.3. 体言止めの範囲を守る

* **使用可**：見出し、表のセル、構成要素の列挙、上位見出しで主語・動詞が明示された箇所。
* **使用を避ける箇所**：仕様の振る舞い定義、手順の指示、ルールの記述では、主語と要否が明確になるよう文末まで書く。

## 4. 表と装飾

* **表**：各項目に複数の属性がある場合（対象・条件・結果、メリット・デメリット、料金・スペックなど）は、Markdownの表にする。
* **太字**（`**`）：段落や箇条書きのグループごとに、強調するキーワードやラベルに絞る。  
  文全体の太字化は避ける。
* **コードスパン**（`` ` ``）：コマンド、ファイル名、パス、変数名、リテラル値、キーボード入力値に限る。  
  一般的な日本語の強調には「」を使う。
* **引用と水平線**：引用ブロック（`>`）の多用や、見出し直前の不要な水平線（`---`）を避ける。
