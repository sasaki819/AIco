# 04. ブランチ運用仕様

## 概要

AIcoにおけるブランチ構成・更新責務・統合手順および並行作業時の運用を定める。
本章では以下を定める。

* ブランチ構成と命名
* ブランチ別の更新責務
* 起票から統合までの手順
* 並行作業と並列実行方式との境界

## 1. ブランチ構成と命名

AIcoは **`main` ← 統合ブランチ ← 作業ブランチ** の3層を基本形とし、管理情報を集約する統合ブランチは常に1本（`aico-manifest.json` の `integration_branch` で指定。既定は `develop`、GitHub Flowでは `main` 等）とする。

* **作業ブランチの命名**：具体的な命名規約は導入先プロジェクト（`AGENTS.md` マーカー外等）に委ねる。
* **記録方法**：起票または着手時に決定した実際の作業ブランチ名を、チケット `index.md` の frontmatter `branch` キーへ記録する（導入先規約がない場合の参考例：`feature/<チケットID>`）。
* **サポート対象外**：`release/*` や `hotfix/*` を含むフルGit Flow専用フローは規定しない。導入先で併用する場合も、管理情報の起票およびダッシュボード・一覧更新は常に単一の統合ブランチ側で行うこと。

## 2. ブランチ別の更新責務

共有ファイルの競合を防ぐため、統合ブランチと作業ブランチの更新範囲を以下のとおり明確に分離する。

| ブランチ | 更新するもの | 更新してはならないもの |
| :--- | :--- | :--- |
| **統合ブランチ** | ・議事録・ADR・Runbookなどの共有情報<br>・チケットの起票（`status: open`）<br>・管理ルートダッシュボード（`management/index.md`）および各区分 `index.md` の再生成 | ・個別チケットの実装途中コード<br>・個別チケット配下の途中進捗 |
| **作業ブランチ** | ・対象チケットの成果物（プロジェクト資産）<br>・対象チケット配下の全記録（`index.md`・`plan.md`・`notes/`・`artifacts/`・`review/`）<br>・対象チケットの `## 変更ファイル` および `review/index.md` の再生成<br>・完了時のチケット `status` 更新（`done` / `cancelled`） | ・`management/index.md` および各区分 `index.md`<br>・他チケットの記録<br>・全体の共有情報（議事録・ADR・Runbook本体） |

## 3. 起票から統合までの手順

1. **起票（統合ブランチ）**：統合ブランチ上でチケットを作成（`status: open`、`phase: drafting`、`phase_status: working`、`branch` 記録）し、一覧・ダッシュボードを再生成してコミットする。その後、ユーザーが必要に応じて push や PR/MR を進める（保護ブランチ等の制約がある場合は導入先の運用に従う）。
2. **作業ブランチ作成・切替**：統合ブランチから `branch` に記録した作業ブランチを作成して切り替える。着手合意（DoR）完了後、`status: in-progress` へ更新して作業を進める。
3. **クロージング準備（作業ブランチ）**：`phase: closing` へ進め、以下を実施する。
   * スクリプトで `index.md` の `## 変更ファイル`（統合ブランチとの差分におけるプロジェクト資産一覧）を生成・更新する。
   * ACごとに結果と根拠を実物照合して `## DoD（完了の定義）` へ記録する。未検証項目がある場合は「受け入れて完了とするか、検証を引き継ぐか」を人間へ確認し、判断結果と追跡先リンクを記録する。
   * 人間の完了承認を得たうえで、作業ブランチ側で `status: done`・`phase: closing`・`phase_status: done` へ更新しコミットする（中止時は `status: cancelled` へ更新し、`phase`・`phase_status` は中止時点の値を維持する）。
4. **統合と一覧再生成（統合ブランチ）**：
   * ユーザーが必要に応じて push・PR/MR またはローカルマージにより作業ブランチを統合ブランチへ統合する（fast-forward / `--no-ff` / squash 等のマージ方式は導入先プロジェクトのGit運用に従う）。
   * 統合ブランチ側で一覧・ダッシュボード再生成スクリプトを実行し、変更をコミットする（チケット実体の `status` は作業ブランチ側で完了済みのため、原則として統合ブランチ側で個別チケットを直接編集しない。ただし作業ブランチ未作成の `open` チケット中止やコード破棄を伴う中止時は、`06`章 `aico-ticket-cancel` の手順に従い統合ブランチ側で `status: cancelled` を直接反映してよい）。
   * なお、一覧・ダッシュボード再生成スクリプトは非対話・べき等に動作するため、導入先プロジェクトの任意構成として統合ブランチ反映をトリガーに CI/CD パイプラインで自動実行する運用も可能とする。
   * マージ済み作業ブランチの削除は導入先プロジェクトの運用に従う。

## 4. 並行作業と並列実行方式との境界

### 4.1. 並行作業時の衝突防止とエスカレーション

複数の作業ブランチを並行して進める場合は、以下を守る。

* **事前確認**：並行着手前に変更予定ファイルと関連仕様の重なりを確認し、共有ファイルが重なる場合は担当または統合順序を調整する。
* **エスカレーション対象**：他作業ブランチの全走査は要求しない。着手前の確認、共有済みの前提、既存ADR、または統合時のマージ競合によって検知した仕様矛盾・競合のみ、判明した事実・選択肢ごとの影響・AIの推奨案を添えて人間へエスカレーションする。
* **未統合進捗の認識**：統合ブランチのダッシュボードおよび一覧には未統合の作業ブランチ上の途中進捗は反映されない。作業中の最新状況は対象作業ブランチのチケット記録で確認する。

### 4.2. 並列実行方式（Git worktree等）との境界

AIcoは Git worktree の構成基準・作成先・削除手順を規定しない。
ただし、作業ブランチを作成・切替してチケット対応を開始する際に、導入先プロジェクト側（`AGENTS.md` マーカー外等）に worktree 等の並列実行方針が定義されている場合は、その方針に従って作業環境を準備すること。
