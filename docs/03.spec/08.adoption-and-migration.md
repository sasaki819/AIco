# 08. 導入・移行・リリース仕様

## 概要

AIco本体の構成、既存プロジェクトへの導入・初期設定・カスタマイズ、およびリリースとアップデートの仕様を定める。
本章では以下を定める。

* AIco 本体のリポジトリ構成とミラー・ドッグフーディング
* 初回導入と初期設定仕様（`install.py` / `init`）
* カスタマイズと上書きルール
* リリースとバージョン管理仕様
* アップデートとマイグレーション仕様（`update` / `upgrade.py`）

## 1. AIco 本体のリポジトリ構成とミラー・ドッグフーディング

### 1.1. 配布テンプレートと運営領域の分離

AIco 本体のリポジトリでは、導入先へ展開する配布テンプレート（`template/`）、導入・移行本体ツール（`installer/`）、自動テスト（`tests/`）、および AIco 自身の開発に用いるドッグフーディング運営領域を明確に分離して管理する。

```text
aico/                                # AIco 本体リポジトリルート
├── README.md                        # AIco 全体の入口・導入案内
├── CHANGELOG.md                     # SemVer 変更履歴・変更意図・移行要否
├── docs/
│   ├── 01.tips/                     # 実践上の小技・設定例などの補足ガイド（任意の参考資料）
│   ├── 02.policy/                   # ポリシー（思想・判断軸）
│   └── 03.spec/                     # 仕様書（01〜08章）
├── template/                        # 導入先へ配布・展開する原本一式
│   ├── AGENTS.md                    # AIco 管理ブロック（AICO:BEGIN〜END）雛形
│   ├── CLAUDE.md                    # @AGENTS.md 参照雛形
│   ├── .agents/skills/aico-*/       # 配布スキル原本（21スキル）
│   ├── tools/aico.{sh,bat}          # 人用ラッパー原本
│   └── management/                  # 既定管理ルート雛形
│       ├── index.md                 # ダッシュボード雛形（summary / active-tickets）
│       ├── aico-manifest.json       # 初期マニフェスト（worker_models はすべて ""）
│       ├── 01.manual/               # Getting Started・詳細規約
│       ├── 02.discussions/index.md
│       ├── 03.adr/index.md
│       ├── 04.tickets/index.md
│       ├── 05.runbooks/index.md
│       ├── templates/               # 記録テンプレート＋workers/worker-{high,middle,low}.md
│       └── scripts/                 # 日次15スクリプト＋init.py・update.py＋_launcher.py＋_lib/
├── installer/                       # 導入・移行本体ツール（配布対象外）
│   ├── install.py                   # 初回資材配置スクリプト
│   ├── upgrade.py                   # アップデート・段階マイグレーション実行本体
│   └── migrations/                  # 版別マイグレーション定義（vX.Y.Z_to_vA.B.C.py 等）
├── tests/                           # 自動テスト（単体・結合・導入／設定／移行テスト、配布対象外）
│
│   # --- 以下は AIco 本体開発用のドッグフーディング運営領域（導入先へ配布しない） ---
├── AGENTS.md                        # AIco 本体自身の運用規約（template/ から導入・同期）
├── CLAUDE.md
├── .agents/                         # AIco 本体自身のスキル・ワーカー
├── .claude/ / .codex/ / .github/    # AIco 本体自身の同期先
├── tools/                           # AIco 本体自身のランチャー
└── management/                      # AIco 本体開発の議事録・ADR・チケット・Runbook
```

* **配布の単一原本**：導入先へ展開するファイルは必ず `template/` 配下から取得し、AIco 本体側の運営領域（ルート直下の `management/` や `.agents/` 等）から直接コピーしてはならない。

### 1.2. 公開リポジトリ・ミラー運用と共通配布元解決

AIco 本体は、開発元リポジトリ（例：自宅 GitLab）から公開ミラー（GitHub：`https://github.com/sasaki819/AIco.git`）へ同一コミット・同一タグをミラーして公開する。複数ミラーやオフライン環境でもスクリプト本体を書き換えずに運用するため、以下を共通仕様とする。

* **既定の配布元リポジトリ**：スクリプト内に保持する既定の配布元 URL は公開向けの `https://github.com/sasaki819/AIco.git` とする。別ミラー（例：自宅 GitLab `https://gitlab.sasaki819.mydns.jp/open/aico.git` や社内ミラー）を利用する場合は `--source` で切り替え、確定した Git URL を導入先の `aico-manifest.json`（`source_repository`）へ保存する。
* **実行場所の統一**：初回導入（`install.py`）、初期設定（`tools/aico.sh init`）、アップデート（`tools/aico.sh update`）のいずれも、**常に導入先プロジェクトのルート（カレントディレクトリ）で実行する**方式へ統一する（`--target` オプションは設けない）。各コマンドはカレントディレクトリが Git リポジトリのルートであることを事前検証する。
* **`--source <値>` の共通解決仕様**：導入・アップデートの双方は、`--source`（または `aico-manifest.json` の `source_repository`）を以下のルールで自動判別して扱う。

| 配布元の種別 | 入力例 | 解決・取得動作 |
| :--- | :--- | :--- |
| **ローカルディレクトリ**<br>（clone 済み／展開済みアーカイブ） | `/path/to/aico`<br>`file:///path/to/aico` | `.git` の有無を問わず、直下に `template/`（更新時は `installer/upgrade.py` も）が存在すればそのまま直接参照する（通信ゼロ・`git clone` 不要）。`.git` のない展開済み zip/tar.gz アーカイブもローカル `git clone` 済みディレクトリと同一処理で扱う |
| **リモート Git リポジトリ URL** | `https://github.com/sasaki819/AIco.git`<br>`https://gitlab.sasaki819.mydns.jp/open/aico.git`<br>`ssh://...` / `git@...` | `git ls-remote --tags <url>` で SemVer タグ（`vX.Y.Z`）を解決し、`git clone --depth 1 --branch <tag> <url> <一時ディレクトリ>` で取得して処理完了後に自動削除する。GitLab・GitHub・社内 Git サーバーの認証設定やプロキシ設定をそのまま利用できる |

* **共有マニフェストの汚染防止**：ローカルパスを一時的に `--source` 指定した場合、個人環境固有のパスがチーム共有の `aico-manifest.json` へ入らないよう、`source_repository` へ自動記録するのはリモート Git URL のみとする（ローカルディレクトリ指定時は既存の `source_repository` を維持し、初回導入でローカル指定のみの場合は `""` とする）。

### 1.3. ドッグフーディングと知見還元

* **開発中の分離原則**：AIco 本体の開発は現行版の運営領域（ルート直下の `management/`・`.agents/` 等）を用いて進め、変更対象は `template/`・`installer/`・`tests/`・`docs/` のみとする。開発途中に運営領域を手作業で新版仕様へ改造してはならない。
* **リリース前の自己適用検証**：PATCH・MINOR を含むすべてのリリースにおいて、タグ発行前に必ず `4.2`節の時系列に従って AIco 本体自身の運営領域へ `tools/aico.sh update --source .`（初回 `v0.1.0` のみ `install.py` → `init`）を適用し、`doctor.py --strict` および全自動テスト通過を確認してからタグを発行する。
* **導入先知見の還元**：導入先プロジェクトの運用で検知した汎用的な改善点・構造的問題は `aico-feedback` 等を通じて AIco 本体の議事録・チケットへ起票し、次版へ継続的に取り込む。

## 2. 初回導入と初期設定仕様（`install.py` / `init`）

初回導入は、性質の異なる **① 資材配置（`installer/install.py`）** と **② 初期設定・再設定（`tools/aico.sh init`）** の2段階に分離する。`install.py` は AIco 未導入プロジェクトへの安全な資材配置のみで完結し、完了後に `tools/aico.sh init` の実行を案内して終了する。

### 2.1. 資材配置（`installer/install.py`）

* **前提条件**：
  * カレントディレクトリが導入先プロジェクトの Git リポジトリルートであること。
  * Python 3.11 以上（原則 `uv` 推奨）および `git` が利用可能であること。
  * 作業ツリーに未コミット変更がないこと（ロールバック可能な状態を確保するため、未コミット変更がある場合は終了コード `1` で停止する。明示解除時は `--allow-dirty`）。
* **実行方法（導入先プロジェクトのルートで実行、PEP 723・標準ライブラリのみ）**：
  * **公開既定（GitHub）から導入**：`uv run https://raw.githubusercontent.com/sasaki819/AIco/vX.Y.Z/installer/install.py`
  * **GitLab ミラーなど別リポジトリから導入**：`uv run https://gitlab.sasaki819.mydns.jp/open/aico/-/raw/vX.Y.Z/installer/install.py --source https://gitlab.sasaki819.mydns.jp/open/aico.git`
  * **ローカル clone／展開済みアーカイブから導入（オフライン）**：`uv run /path/to/aico/installer/install.py`（スクリプトと同一リポジトリ配下に `template/` が存在する場合は自動検出し、通信ゼロで動作する）
  * **`uv` を利用しない環境での導入**：URL からの直接実行は `uv` 固有の機能であるため、`uv` が利用できない環境ではリポジトリを一時 `git clone`（またはリリースアーカイブを展開）したうえで、導入先プロジェクトルートから `python3 /path/to/aico/installer/install.py`（Windows は `py -3 /path/to/aico/installer/install.py`）を実行する（導入後の `tools/aico.{sh,bat}` は `uv` 不在時に自動で `python3` / `py -3` へフォールバックする）

※`uv run <URL>` 実行時は、Python スクリプト内から起動元 URL を自動取得できないため、スクリプト内の既定配布元（`https://github.com/sasaki819/AIco.git`）と埋込版定数（`AICO_VERSION`）、または明示指定の `--source` / `--ref` を用いて取得元を確定する。なお、可変ブランチや `latest` タグの URL を用いる場合は、`uv` の URL キャッシュにより旧版が再実行されることがあるため `uv run --refresh <URL>` の利用を推奨する。

| オプション | 必須／任意 | 既定値 | 説明 |
| :--- | :--- | :--- | :--- |
| `--source <path\|url>` | 任意 | 隣に `template/` があればそのディレクトリ、なければ `https://github.com/sasaki819/AIco.git` | 配布元のローカルディレクトリ（clone 済み／展開済みアーカイブ）またはリモート Git リポジトリ URL |
| `--ref <tag>` | 任意 | スクリプト内の `AICO_VERSION` に対応する `vX.Y.Z` タグ | リモート Git 取得時に使用するタグまたはブランチ（ローカルディレクトリ指定時は参照しない） |
| `--management-root <name>` | 任意 | `management` | 導入先で使用する管理ルート名（既存 `management/` との衝突回避用） |
| `--dry-run` | 任意 | 無効 | 実ファイルを一切変更せず、配置・追記予定のみを表示 |
| `--allow-dirty` | 任意 | 無効 | 未コミット変更がある作業ツリーでの実行を明示許可 |
| `--json` | 任意 | 無効 | `07`章と同一の共通スキーマで結果を JSON 出力 |

`installer/install.py` は既存プロジェクトのソースコード・設計書・固有設定を上書きしないよう、以下の手順で安全に展開する。

1. **事前検証と衝突検査**：
   * カレントディレクトリが Git リポジトリルートであること、および作業ツリーがクリーンであることを確認する（違反時は終了コード `1`）。
   * 指定された `--management-root`、`tools/aico.sh` / `tools/aico.bat`、`.agents/skills/aico-*` に既存の未管理ファイルが存在する場合は上書きせず終了コード `1` で停止し、`--management-root` の変更または事前退避を案内する。
   * `AGENTS.md` がすでに存在し `<!-- AICO:BEGIN -->` を含む場合は既存導入済みと判断して終了コード `1` で停止し、`tools/aico.sh update` の利用を案内する。
   * 既存の `CLAUDE.md` が `@AGENTS.md` 以外の独自記述を持つ場合は上書きせず終了コード `1` で停止し、独自内容を `AGENTS.md` のマーカー外へ退避してから再実行するよう案内する。
2. **テンプレート展開と初期マニフェスト配置**：
   * `1.2`節の解決仕様で取得した `template/` 配下の AIco 由来ファイルおよび空の初期管理ルートをカレントの導入先リポジトリへ配置する。
   * `AGENTS.md` が既存の場合は既存本文を一切変更せず末尾へ `<!-- AICO:BEGIN -->` 〜 `<!-- AICO:END -->` ブロックを追記する。未存在の場合は新規作成する。
   * `aico-manifest.json` へ `schema_version`・`aico_version`・`management_root`・`source_repository`（リモート Git URL 使用時のみ記録、ローカル指定時は `""`）を書き込む（`worker_models` の `model`・`effort` はすべて初期値 `""` とする）。
   * `--management-root` が既定の `management` 以外の場合は、`tools/aico.sh`・`tools/aico.bat` の既定参照パスへ反映する。
3. **次ステップの案内**：
   * 配置結果を表示し、次ステップとして `tools/aico.sh init`（Windows は `tools/aico.bat init`）の実行を案内して終了する（自動 `git commit` は行わない）。

### 2.2. 初期設定・再設定（`tools/aico.sh init`）

導入先固有の運用パラメータ設定とツール同期・診断は、配布済みスクリプト `management/scripts/init.py`（入口：`tools/aico.sh init` / `tools/aico.bat init`）が担う。初回導入直後だけでなく、運用開始後のツール追加・統合ブランチ変更・配布元ミラー切替・モデル見直し時にも何度でも再実行できる。

* **対話モードと非対話モード**：
  * **対話モード（設定引数なし＋TTY 接続時）**：現在の `aico-manifest.json` の値（初回は既定値および Git ブランチからの推定値）を提示しながら、統合ブランチ・利用ツール・配布元 URL・各ツールの `worker_models`（`model` / `effort`）を対話形式で設定できる。
  * **非対話モード（設定引数あり、または非 TTY 時）**：標準入力待ちを行わず、指定されたオプション値（未指定項目は既存の `aico-manifest.json` の値または既定値）でマニフェストを更新し、同期・再生成・診断を実行する。

| オプション | 必須／任意 | 既定値 | 説明 |
| :--- | :--- | :--- | :--- |
| `--integration-branch <branch>` | 任意 | 既存値、未設定時は Git ブランチから推定（`develop` 優先、なければ `main` 等） | 導入先の統合ブランチ名 |
| `--tools <list>` | 任意 | 既存値、未設定時は `claude,codex,antigravity,copilot` | 有効化する AI ツール一覧（カンマ区切り） |
| `--source <url>` | 任意 | 既存値を維持 | `aico-manifest.json` の `source_repository` に保存するアップデート参照先 Git URL（オフライン専用時は `""`） |
| `--dry-run` | 任意 | 無効 | 実ファイルを変更せず、更新予定と同期予定のみを表示 |
| `--json` | 任意 | 無効 | `07`章と同一の共通スキーマで結果を JSON 出力 |

* **実行手順**：
  1. `aico-manifest.json` を原子的に更新する。
  2. `sync_agents.py` → `rebuild_indexes.py` → `doctor.py` を順に実行し、設定反映結果および未設定項目（`worker_models` の `WARN` 等）を報告して終了する（自動 `git commit` は行わない）。

### 2.3. 導入直後の確認チェックリスト（人間作業）

`install.py` 完了後、導入先プロジェクトでは以下の3ステップを実施してから運用を開始する。

1. `tools/aico.sh init`（Windows は `tools/aico.bat init`）を実行し、統合ブランチ・利用ツール・配布元 URL・各ツールの `worker_models`（`high` / `middle` / `low` の `model` と `effort`）を設定・反映する（`worker_models` は `management/aico-manifest.json` を直接編集したうえで `tools/aico.sh sync_agents` を実行してもよい）。
2. `AGENTS.md` のマーカー外へ、導入先固有のビルド・テスト手順、作業ブランチ命名規約、worktree 方針、レビュー実施基準等を追記する。
3. `tools/aico.sh doctor` を実行して `ERROR` 0件を確認し、利用する AI ツールで `AGENTS.md` とスキルが実際に読み込まれることを確認してから初回コミットを行う。

## 3. カスタマイズと上書きルール

将来のアップデートで導入先固有の設定や作業記録を失わないため、許可されるカスタマイズと禁止事項を以下のとおり定める。

| 区分 | 対象 | ルール |
| :--- | :--- | :--- |
| **許可（プロジェクト固有領域）** | ・`AGENTS.md`（マーカー外）<br>・`management/aico-manifest.json`<br>・`.agents/skills/<固有スキル名>/`（`aico-` 以外）<br>・各ツール `agents/` 配下の固有エージェント（`worker-{high,middle,low}.*` 以外）<br>・管理ルート外の固有ツール・設計書 | 導入先が自由に編集・追加できる。AIco 標準規約をプロジェクト方針で上書きしたい場合は、AIco 由来領域を直接書き換えず `AGENTS.md` マーカー外へ変更内容と理由を明記する |
| **禁止（AIco 由来領域）** | ・`AGENTS.md`（マーカー内）<br>・`CLAUDE.md`<br>・`.agents/skills/aico-*` および同期先スキル<br>・`worker-{high,middle,low}.*`<br>・`tools/aico.*`<br>・`management/01.manual/`・`templates/`・`scripts/` | 導入先で直接改造してはならない。構造的な問題や汎用改善要望がある場合は `aico-feedback` で共有し、AIco 本体のアップデートで取り込む |

## 4. リリースとバージョン管理仕様

### 4.1. セマンティックバージョニング（SemVer）基準

AIco の版は `MAJOR.MINOR.PATCH`（Git タグ：`vMAJOR.MINOR.PATCH`）で管理する。

| 版の種別 | 変更内容の基準 | マイグレーション要否 |
| :--- | :--- | :--- |
| **PATCH（`x.y.Z`）** | 誤字修正、スクリプトの不具合修正、既存記録・設定スキーマに影響しない内部改善 | 不要 |
| **MINOR（`x.Y.0`）** | 後方互換のあるスキル・スクリプト・オプション追加、テンプレート任意項目追加、既存記録の変換を伴わない拡張 | 原則不要（設定項目追加等がある場合は後方互換マイグレーションを提供） |
| **MAJOR（`X.0.0`）** | ディレクトリ構成・命名規則・frontmatter 必須キー・ステータス語彙・`aico-manifest.json` の `schema_version` 変更など既存記録や設定へ影響する変更 | **必須**（検証済みの移行手順とマイグレーションスクリプトを同梱） |

※`0.y.z`（初期開発フェーズ）であっても、導入先の既存記録・設定へ影響する変更を含むリリースでは `MAJOR` と同様に必ずマイグレーション手順とスクリプトを提供する。

### 4.2. `CHANGELOG.md` とリリース・自己適用手順

* **`CHANGELOG.md` の必須記載項目**：各バージョンごとに「リリース日・タグ」「変更内容」「**変更意図（なぜ変更したか）**」「移行要否と具体的な移行手順」「検証済み環境および未確認環境（OS・AIツール）」を記載する。
* **リリースおよびドッグフーディング自己適用の時系列**：タグ発行後のタグ打ち直しや、`template/` と運営領域の版ズレを防ぐため、すべてのリリース（PATCH・MINOR を含む）は以下の 4 段階を厳密に順序どおり実施する。

| 段階 | ブランチ | 実施内容 | `template/` の版 | AIco 運営領域の版 |
| :--- | :--- | :--- | :--- | :--- |
| **1. 通常開発** | 作業ブランチ → 統合ブランチ | 現行版の運用ルールで `template/`・`installer/`（`migrations/` 含む）・`tests/`・`docs/` を開発・マージする。ルート直下の運営領域は手作業で新版仕様へ改造しない | 旧版（開発中） | 旧版 |
| **2. リリース準備コミット** | 統合ブランチ | `template/management/aico-manifest.json` の `aico_version`、`installer/install.py` の埋込版定数（`AICO_VERSION`）、および `CHANGELOG.md` を次版へ更新してコミットする（作業ツリーをクリーン化）。`tests/` の全自動テスト成功を確認する | 次版 | 旧版 |
| **3. ドッグフーディング自己適用＆検証** | 統合ブランチ | AIco リポジトリのルートで `tools/aico.sh update --source .` を実行して運営領域を旧版から次版へ移行する（初回 `v0.1.0` のみ `uv run installer/install.py` → `tools/aico.sh init`）。`tools/aico.sh doctor --strict` および `tests/` 全件の終了コード `0` を確認し、自己適用差分をコミットする | 次版 | 次版 |
| **4. タグ発行・ミラー公開** | 統合ブランチ（または `main` マージ後） | 自己適用コミットまで含めた最終状態へ `vX.Y.Z` タグを発行し、開発元リポジトリ（GitLab）へプッシュして公開ミラー（GitHub）へ同一コミット・同一タグを反映する | 次版 | 次版 |

* **段階 2 と段階 3 を別コミットに分ける理由**：`update` の事前ガード（作業ツリーがクリーン・統合ブランチ上・現在版 < 目標版）を例外フラグなしで満たし、導入先ユーザーと同一の移行経路を検証するためである。
* **段階 3 で不具合を検知した場合**：タグ未発行の状態であるため、自己適用差分をロールバックして `template/` または `installer/` を修正し、段階 2 からやり直す。

## 5. アップデートとマイグレーション仕様（`update` / `upgrade.py`）

### 5.1. 2層構成（入口 `tools/aico.sh update` ＋実行本体 `installer/upgrade.py`）

アップデートは場当たり的な手作業コピーを避け、導入先内の薄い入口（`management/scripts/update.py`）と、目標版リポジトリに同梱される実行本体（`installer/upgrade.py`＋`installer/migrations/`）の2層構成で実行する。

* **入口（`tools/aico.sh update` / `tools/aico.bat update`）の責務**：
  1. 導入先の `aico-manifest.json` から現在版（`aico_version`）と配布元（`source_repository`）を読み取る。
  2. `1.2`節の解決仕様に従い、現在版と目標版（リモート Git なら最新の安定 SemVer タグまたは `--to` 指定タグ、ローカルディレクトリならそのツリーの `aico_version`）を比較して更新要否を表示する（`--check` 時はここで終了）。
  3. 目標版のリポジトリ一式（`template/`・`installer/upgrade.py`・`installer/migrations/`）をローカル参照または一時ディレクトリへ取得し、**目標版側の `installer/upgrade.py`** をサブプロセスとして起動して実処理を委譲する。
* **目標版側への委譲理由**：差し替えとマイグレーションを常に目標版の `installer/upgrade.py` が担うことで、将来の大きな構造変更（例：`v1 → v2`）でも旧版側の `update.py` の仕様制約を受けずに移行できる。
* **非常口**：万一導入先側の `update.py` が破損している場合でも、導入先プロジェクトのルートから目標版の `installer/upgrade.py` を直接起動（`uv run <raw URL またはローカル>/installer/upgrade.py [--source ...]`）できる。

| オプション（`tools/aico.sh update`） | 必須／任意 | 既定値 | 説明 |
| :--- | :--- | :--- | :--- |
| `--check` | 任意 | 無効 | 現在版と目標版の比較・更新要否の確認のみを行い、実ファイルを変更せず終了コード `0` で終了（`--json` で更新有無と版差分を返却） |
| `--to <vX.Y.Z>` | 任意 | 最新安定タグ（ローカル指定時はそのツリーの版） | 更新先の目標バージョンを明示指定 |
| `--source <path\|url>` | 任意 | `aico-manifest.json` の `source_repository` | 配布元を一時的に上書き指定（ローカル clone・展開済みアーカイブ・別ミラーに対応） |
| `--dry-run` | 任意 | 無効 | 実ファイルを一切変更せず、差し替え予定・実行予定マイグレーションを表示 |
| `--json` | 任意 | 無効 | `07`章と同一の共通スキーマで結果を JSON 出力 |

* **前提条件（事前ガード、`--check` 時は確認のみ実施）**：
  * カレントディレクトリが導入先プロジェクトの Git リポジトリルートであること。
  * 作業ツリーに未コミット変更がないこと（Git で即座にロールバックできる状態を保証。未コミット時は終了コード `1` で停止）。
  * 導入先の現在ブランチが `aico-manifest.json` の `integration_branch` であること（作業ブランチ上での誤アップデートを防止）。
  * 導入先の `aico_version` が目標版より古いこと（ダウングレードや未知バージョン指定は終了コード `1` で拒否。同一版での再実行は差分確認・べき等終了とする）。
* **破壊操作の抑止**：自動 `git commit`・自動 `git push` は行わない。

### 5.2. 段階的アップデート手順

目標版側の `installer/upgrade.py` は以下の 5 ステップを順序どおりに実行する。

1. **移行経路の解決**：導入先の `aico-manifest.json` から現在版を読み取り、目標版までのマイグレーション経路（複数バージョン跨ぎの場合は中間版を飛ばさず `vA → vB → vC` と逐次連鎖）を解決する。経路が途切れている場合は終了コード `1` で停止する。
2. **AIco 由来領域の安全な差し替え**：
   * `AGENTS.md` は `<!-- AICO:BEGIN -->` 〜 `<!-- AICO:END -->` 内部のみを最新版へ置換し、マーカー外は一切変更しない。
   * `.agents/skills/aico-*` は最新版へミラー差し替えする（旧版で廃止された `aico-*` は削除し、導入先固有スキルは保持する）。
   * `management/01.manual/`・`management/templates/`・`management/scripts/`・`tools/aico.*`（導入先の `management_root` を維持）を最新版へ差し替える。内容に差分がないファイルは書き換えをスキップし、Windows の `tools/aico.bat` 自己更新時も安全に完了する構造（`07`章`3.1`節）を維持する。
   * 作業記録領域（`02.discussions/`〜`05.runbooks/`）およびプロジェクト固有領域は、このステップでは一切上書きしない。
3. **マイグレーションスクリプトの逐次実行**：
   * `installer/migrations/` に配置された該当版間のスクリプトを古い順にすべて実行する。
   * 各マイグレーションスクリプトは以下の契約を実装し、原子的更新かつべき等であること。
     * `FROM_VERSION` / `TO_VERSION`：対象バージョン境界の明示宣言
     * `check(ctx)`：前提条件・対象構造の妥当性検査
     * `plan(ctx)`：`--dry-run` 用の変更予定リスト生成
     * `apply(ctx)`：既存記録・`aico-manifest.json` 等の安全な変換適用
     * `verify(ctx)`：変換後のスキーマ・リンク整合検証
4. **マニフェスト更新・同期・一覧再生成**：
   * `aico-manifest.json` の `aico_version`（および変更時は `schema_version`）を最新版へ更新する（`management_root`・`integration_branch`・`source_repository`・`tools`・`worker_models` の導入先固有値は保持する）。
   * 最新版の `sync_agents.py` と `rebuild_indexes.py` を実行し、同期先スキル・ワーカー定義・`CLAUDE.md`・全一覧を再生成する。
5. **適用後診断**：
   * 最新版の `doctor.py` を実行し、版一致・設定過不足・リンク切れ・frontmatter 規約・マーカー整合を確認して結果を報告する。

### 5.3. 想定外エラー時の停止と復旧

* 事前検査・差し替え・マイグレーション・事後診断のいずれかでエラー（終了コード `1`）が発生した場合、`upgrade.py` は後続ステップを即座に停止し、失敗したステップ／マイグレーション名・対象ファイル・原因を明示出力する。
* AI は失敗した移行を手作業のファイル編集で強行継続してはならない。人間へ状況を報告し、Git による作業前コミットへのロールバックを含めて復旧方針を合意する。
* AIco 側のマイグレーション不具合が原因と判断した場合は、`aico-feedback` で事象を整理して AIco 本体へ報告する。

### 5.4. 導入・初期設定・移行テスト仕様

`tests/` 配下には、日次スクリプトテスト（`07`章）に加えて以下の導入・初期設定・移行結合テストを必須整備する。

| テスト対象 | 必須検証ケース |
| :--- | :--- |
| **`installer/install.py`** | ・新規リポジトリおよび既存コード・既存 `AGENTS.md` を持つリポジトリのルートからの安全な資材配置（マーカー外保持）<br>・リモート Git（模擬リポジトリ）、ローカル `git clone` 済みディレクトリ、および `.git` を持たない展開済みアーカイブの3系統からの導入<br>・ローカル `--source` 指定時に個人パスが `aico-manifest.json` の `source_repository` へ書き込まれないこと<br>・`--management-root` カスタム名での導入と `tools/aico.*` 追従<br>・Git ルート外実行・未管理ファイル衝突・既存導入済み・独自 `CLAUDE.md` 衝突時の非変更停止（終了コード `1`）、`--dry-run` 非変更保証 |
| **`management/scripts/init.py`** | ・初回導入後の非対話設定（`--integration-branch`・`--tools`・`--source`）および再実行による設定変更が `aico-manifest.json`・同期先スキル・ワーカー定義・`CLAUDE.md` へ正しく反映されること<br>・TTY 対話モードおよび非 TTY 時の非停止動作、`--dry-run` 非変更保証、初期化後の `doctor.py` で `ERROR` 0件 |
| **`management/scripts/update.py`<br>`installer/upgrade.py`** | ・`--check` による現在版／最新版の比較と非変更終了、`--to` 版指定、リモート Git・ローカル clone・`.git` なし展開済みアーカイブからの更新と目標版 `upgrade.py` への委譲<br>・旧版模擬リポジトリ（既存作業記録・`AGENTS.md` マーカー外記述・導入先固有スキル・導入先固有エージェント・`source_repository`・`worker_models` 設定値を含む）へのアップデートで固有資産が一切失われないこと<br>・複数バージョン跨ぎの逐次マイグレーション、同版再実行のべき等性、`--dry-run` 非変更保証<br>・未コミット変更あり・作業ブランチ上・ダウングレード指定・マイグレーション失敗時の安全停止（終了コード `1`） |
