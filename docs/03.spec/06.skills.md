# 06. スキル仕様

## 概要

AIcoの全作業工程をスキルベースで進めるための共通規約および各スキルの仕様を定める。
本章では以下を定める。

* スキル共通仕様と設計規約
* スキル一覧と状態遷移マッピング
* 各スキルの入出力と手順仕様
* Markdown文書作成スキル仕様

## 1. スキル共通仕様と設計規約

### 1.1. 配置と命名

* **原本の配置**：すべてのスキルは `.agents/skills/<skill-name>/SKILL.md` を原本とする。長い補足手順や具体例は同一ディレクトリ配下の `references/` へ分離する。
* **命名規則**：省略形を使わずフルスペルで記述し、以下の3パターンで命名する。
  * **新規作成**：`aico-create-<対象>`（例：`aico-create-ticket`、`aico-create-adr`、`aico-create-runbook`）
  * **既存対象への操作**：`aico-<対象>-<動作>`（例：`aico-ticket-start`、`aico-ticket-plan`、`aico-runbook-run`）
  * **単独動詞・横断機能**：`aico-<動作>`（例：`aico-discuss`、`aico-review`、`aico-archive`、`aico-doctor`）
* **名前の一致**：フォルダ名 `<skill-name>` と `SKILL.md` の YAML frontmatter の `name` は必ず一致させること。

### 1.2. 共通書式

すべての `SKILL.md` は UTF-8（BOMなし）・LF改行とし、以下の構造で記述する。

```markdown
---
name: aico-<スキル名>
description: <いつ・何のためにこのスキルを使うかを明確に記述>
---

# aico-<スキル名>

## 目的
## 入力
## 前提条件
## 手順
## 完了条件と状態更新
## 報告形式
```

### 1.3. 入力解決の共通ルール

特定ツールの拡張フィールド（`argument-hint` や `$ARGUMENTS` 等）には依存せず、対象チケットIDや対象記録IDを必要とするスキルは、以下の3段階フォールバックで対象を解決する。

1. **明示指定**：ユーザーがコマンド引数または会話文中で対象ID・`slug`・識別情報を指定している場合はそれを使用する。
2. **作業ブランチからの自動特定**：指定が省略された場合、`ticket_status.py`（`07`章）等を用いて現在のGitブランチ名と `management/04.tickets/*/index.md` の `branch` 属性を照合し、一致するチケットを自動特定する。
3. **候補提示と確認**：統合ブランチ上にある場合や一致候補が0件・複数の場合など自動特定できないときは、該当状態の候補一覧を提示して人間に選択してもらう。

### 1.4. 前提条件と状態更新の原則

状態管理（`status`・`phase`・`phase_status`）を扱うスキルは、以下の原則で前提確認と状態更新を行う。

* **前提条件の確認（ガード＋確認）**：実行前にチケットの `status`・`phase`・`phase_status` および実行ブランチを確認する。期待状態と異なる場合（手戻り等）は即座に処理を進めず、現在状態と差分を人間へ提示し、続行・状態補正の承認を得てから着手すること。
* **完了時の状態更新（承認後更新）**：スキルの作業結果について人間の承認を得た後、次の予定状態へ frontmatter を更新して終了する。
* **分岐する遷移先の合意**：レビュー実施の有無や次フェーズのスキップなど遷移先が分岐する場合は、AIが候補と推奨を提示し、人間と合意した行き先へ更新する。

### 1.5. 禁止事項と他層との責務分離

* **ツール依存構文の禁止**：特定ツール専用の引数展開やコマンド埋め込み構文に依存せず、4ツール共通で解釈できる平易な文章で記述する。
* **スクリプトへの委譲**：記録ファイルの新規作成、frontmatter更新、一覧・変更ファイル再生成、アーカイブ移動、同期、診断などの機械処理はスキル内へ手順を複製せず、`07`章で定める共有スクリプトを呼び出すこと。
* **ワーカーへの委譲**：サブエージェントを使う場合は `worker-high`・`worker-middle`・`worker-low` の役割名のみを指定し、`05`章の5項目委譲規約（手順書パス・対象範囲・入力条件・変更可否・期待成果）を必ず明示する。
* **Markdown品質の適用**：管理記録の作成・編集を伴うすべてのスキルは、`aico-markdown-write` の規約に従って記述する。

※導入・アップデート・マイグレーション手順は日次の開発工程とは切り離し、`08`章で扱う。

## 2. スキル一覧と状態遷移マッピング

### 2.1. 全スキル一覧（21スキル）

### 2.2. `aico-ticket-status` による推奨次スキルの決定表

セッション開始時・再開時に `aico-ticket-status` がチケット実物から次に提案するスキルは、以下の対応表に従って一意に決定する。

| チケット状態（`status` / `phase` / `phase_status`） | 推奨する次スキル |
| :--- | :--- |
| `open` / `drafting` / `working` | `aico-ticket-start` |
| `in-progress` / `planning` / `working` | `aico-ticket-plan` |
| `in-progress` / `design` / `working` | `aico-ticket-design` |
| `in-progress` / `implementation` / `working` | `aico-ticket-implement` |
| `in-progress` / `closing` / `working` | `aico-ticket-close` |
| `in-progress` / `<phase>` / `reviewing` | `aico-review` |
| `in-progress` / `<phase>` / `triaging` | `aico-review-triage` |
| `in-progress` / `<phase>` / `fixing` | `aico-review-fix` |
| `in-progress` / `<phase>` / `re-reviewing` | `aico-review-recheck` |
| `done` または `cancelled`（未統合・一覧未反映時） | 統合ブランチへのマージおよび一覧再生成（`aico-ticket-close` または `aico-ticket-cancel` の統合後手順） |
| `done` または `cancelled`（統合・一覧反映済み） | 追加作業不要（必要に応じ `aico-archive`、または新規作業として `aico-discuss`・`aico-create-ticket` 等を案内） |
| 対象チケットなし（統合ブランチ上・未特定時） | 進行中チケット一覧から再開対象を選択、または新規作業起点（`aico-discuss`・`aico-create-ticket`・`aico-runbook-run` 等）を案内 |
| 上記以外（不正な組み合わせ・状態不整合・値欠損） | 自動進行せず異常状態を人間へ警告し、`aico-doctor` 実行または実物照合による状態補正（人間承認後）を案内 |

## 3. 各スキルの入出力と手順仕様

※対象チケットIDや記録IDの入力を省略した場合は、すべて1.3節の入力解決ルールに従って対象を特定する。
※各スキルの `委譲ワーカー` は、**必須（独立コンテキスト必須）**・**推奨（積極委譲）**・**必要時（大規模時）** の3段階で示し、記載がないスキルは原則メインセッションのみで完結する。

### 3.1. 横断・運用系スキル

#### `aico-archive`

* **目的**：参照頻度の低い完了済み記録を各区分の `archived/` へ安全に移動する。
* **入力**：アーカイブ対象の記録IDまたはパス。
* **前提条件**：統合ブランチ上であること、および `07`章のアーカイブ可否基準を満たすこと（議事録・チケット・Runbook実施記録は `closed`、ADRは `deprecated` または `cancelled`、Runbook手順書は配下に実施中記録がないこと）。
* **委譲ワーカー**：推奨：`worker-low`（`--dry-run`・影響リンク要約および承認後の本実行。親セッションは人間への提示と承認取得に専念）。
* **手順**：
  1. 対象記録と被参照リンクの影響範囲をアーカイブスクリプトの `--dry-run` で確認し、人間へ提示して承認を得る。
  2. アーカイブスクリプトを実行し、`archived/` への移動・リンク追従・一覧再生成を行う。
* **報告形式**：移動元／移動先パス、更新したリンク件数、一覧再生成結果。

#### `aico-doctor`

* **目的**：AIco環境の整合性を診断し、問題点と修復手段を提示する。
* **入力**：なし（任意で修復方針の指定）。
* **委譲ワーカー**：推奨：`worker-low`（`doctor` スクリプト実行・結果整理・修復コマンド抽出および承認後の修復実行。親セッションは人間への報告と承認取得に専念）。
* **手順**：
  1. `doctor` スクリプトを実行し、Python/`uv`・マニフェスト・ワーカーモデル未設定・スキル同期ドリフト・マーカー整合・frontmatter規約・リンク切れを確認する。
  2. エラーまたは警告がある場合は原因と具体的な修復コマンド（同期スクリプト実行、マニフェスト追記等）を提示し、人間の承認後に修復を実施する。
* **報告形式**：検査項目ごとの OK / WARN / ERROR 一覧と推奨対処。

#### `aico-feedback`

* **目的**：適用先プロジェクトで検知したAIcoの構造的問題や改善要望を、AIco開発者へ改修依頼として共有できる構造化Markdown形式で出力する（具体的な外部連携手段は未定のため、連携すべき内容のMarkdown出力に徹する）。
* **入力**：検知した問題・改善要望の要点（任意で該当スキル名・スクリプト名・エラー内容等）。
* **委譲ワーカー**：必要時：`worker-low`（事象ログ抽出・機密マスク整形）、`worker-high`（構造原因の深掘り・改修提案作成時）。
* **手順**：
  1. 対象事象が発生した工程・スキル・スクリプトを確認し、`management/aico-manifest.json` から導入済みAIcoの版（`aico_version`）と利用ツール情報を補完する。
  2. 適用先プロジェクト固有の業務機密・個人情報・認証情報等が含まれないよう、必要に応じて一般化・マスクする。
  3. 以下の必須／任意項目を含むMarkdown形式でフィードバック内容を整形して出力する。
     * タイトル
     * 適用先プロジェクト名（あわせて `aico_version`・利用ツール名）
     * 状況
     * 期待した動作
     * 実際の動作
     * 再現手順
     * 改修提案（任意）
* **報告形式**：そのまま転記・連携できるMarkdownブロック（コードブロックまたは整形済みMarkdown）。

### 3.2. 相談・ADR・Runbook系スキル

#### `aico-discuss`

* **目的**：相談・構想の壁打ちを進め、経緯と結論を議事録へ構造化して残す。
* **入力**：相談テーマ（新規作成時は `slug`・件名、継続時は既存議事録ID）。
* **前提条件**：統合ブランチ上であること。
* **委譲ワーカー**：必要時：`worker-high`（深い背景調査・構成検討）、`worker-low`（既存ADR・議事録の横断確認）。
* **手順**：
  1. 新規時はスクリプトで議事録を作成し、関連する既存ADR・議事録・コードを確認する。
  2. 確認した事実と仮説を分けて人間と議論し、合意事項・理由・選択肢・未決事項を記録する。
  3. 結論に応じて `status`（`in-progress` / `done` / `cancelled`）を更新し、必要なら `aico-create-adr` または `aico-create-ticket` へ接続して相互IDを記録し、一覧を再生成する。
* **報告形式**：議事録パス、`status`、合意要点、未決事項、次の推奨アクション（ADR化・起票等）。

#### `aico-create-adr`

* **目的**：複数作業に影響する設計判断をADRとして記録し、既存判断との整合を保つ。
* **入力**：決定テーマ、`slug`、関連する議事録・チケットID、置換対象ADR（ある場合）。
* **前提条件**：統合ブランチ上であること（作業ブランチ上の議論から発生した場合は、統合ブランチへ切り替えて記録するか、記録タイミングを人間へ確認する）。
* **委譲ワーカー**：必要時：`worker-high`（代替案比較・影響調査）、`worker-low`（既存ADRの重複確認）。
* **手順**：
  1. 既存ADRの重複・矛盾を確認する。
  2. スクリプトでADRを作成し、概要・背景・決定事項・採用理由・不採用案・影響と見直し条件を記入する。
  3. 人間承認後、`update_frontmatter.py` で `status` を `accepted`（検討継続時は `open`）へ更新する。既存ADRを置換する場合は承認後の `accepted` 確定時に `--supersedes` で旧ADRを `deprecated`＋`superseded_by` 設定へ同時更新し、一覧を再生成する。
* **報告形式**：ADRパス、`status`、決定要旨、置換した旧ADR（ある場合）。

#### `aico-create-runbook`

* **目的**：繰り返し実施する定常作業を手順書として作成または改訂する。
* **入力**：Runbook の `slug`・件名・対象手順（改訂時は既存 `slug`）。
* **前提条件**：統合ブランチ上であること。
* **委譲ワーカー**：必要時：`worker-middle`（既存資料からの手順構造化）、`worker-low`（過去ログからの手順抽出）。
* **手順**：
  1. 新規時はスクリプトで `management/05.runbooks/<slug>/runbook.md` を生成する。
  2. 概要・前提条件・入力・手順・完了条件・異常時の対応・改訂履歴を記入し、人間承認を得る。
  3. 一覧を再生成する。
* **報告形式**：Runbookパス、変更要点、一覧再生成結果。

#### `aico-runbook-run`

* **目的**：Runbook手順書に従って定常作業を実施し、実施記録と添付物を残す。
* **入力**：対象Runbookの `slug`（再開時は既存実施記録ID）。
* **前提条件**：統合ブランチ上であること、対象 `runbook.md` が存在すること。
* **委譲ワーカー**：推奨：`worker-low`（定型コマンド実行・ログ抽出）。
* **手順**：
  1. 新規実施時はスクリプトで実施記録フォルダ（`records/<YYYYMMDD-HHMMSS>-<slug>/index.md`）を作成する。
  2. 手順書の前提条件・入力・各ステップを順に実施し、ログや出力ファイル等の添付物を同一記録フォルダへ格納する。
  3. 完了条件を検証する（未検証項目がある場合は人間へ判断を求め、判断結果と追跡先を記録する。実施結果に独立レビューが必要な場合は `aico-review` 以降のレビュー系スキルで `review/` 配下に証跡を残す）。
  4. 異常や改善課題が見つかった場合は、`aico-discuss` または `aico-create-ticket` へ引き継ぎ `followups` を相互参照させる。
  5. `status`（`done` / `cancelled`、中断時は `in-progress`）を更新し、一覧を再生成する。
* **報告形式**：実施記録パス、`status`、完了条件の検証結果、添付物一覧、引き継ぎ先（ある場合）。

### 3.3. チケット系スキル

#### `aico-create-ticket`

* **目的**：ゴールのある作業をチケットとして起票し、概要・AC・DoRの初版を整える。
* **入力**：件名、`slug`、目的・背景、関連する議事録・ADR・親チケットID（任意）、作業ブランチ名（導入先規約に従う）。
* **前提条件**：統合ブランチ上であること。
* **手順**：
  1. 作業ブランチ名を導入先規約に従って確定する（規約がない場合は `feature/<チケットID>` を参考例とする）。
  2. スクリプトでチケットフォルダ一式を生成する（`status: open`、`phase: drafting`、`phase_status: working`、`branch` 記録）。
  3. `index.md` の概要・AC・DoR（任せる範囲・未決事項）・関連リンクを記入し、一覧・ダッシュボードを再生成する。
  4. コミットし、ユーザーが必要に応じて push や PR/MR を進められる状態を提示する。
* **状態更新**：`status: open` / `phase: drafting` / `phase_status: working`。
* **報告形式**：チケットID・パス、決定した作業ブランチ名、AC・未決事項の要約、次スキル（`aico-ticket-start`）の案内。

#### `aico-ticket-start`

* **目的**：DoR（着手合意）を完了し、作業ブランチを準備してチケット対応を開始する。
* **入力**：対象チケットID（省略可）。
* **前提条件**：`status: open`・`phase: drafting`・`phase_status: working` であること。
* **委譲ワーカー**：必要時：`worker-low`（進行中チケットが多い場合の変更予定箇所・共有前提の重複スキャン）。
* **手順**：
  1. チケットの AC・任せる範囲・未決事項を人間と確認し、着手を妨げる未決事項を解消して `## DoR（着手合意）` を確定する。
  2. 並行作業中の他チケットと変更予定ファイル・共有前提の重なりがないか事前確認する。
  3. 統合ブランチから `branch` に記録された作業ブランチを作成・切替する（導入先に worktree 方針がある場合はその方針に従って作業環境を準備する）。
  4. 作業ブランチ側で frontmatter を `status: in-progress`・`phase: planning`・`phase_status: working` へ更新する。
* **状態更新**：`status: in-progress` / `phase: planning` / `phase_status: working`。
* **報告形式**：切替先ブランチ（および worktree パス）、合意したDoR要点、次スキル（`aico-ticket-plan`）の案内。

#### `aico-ticket-plan`

* **目的**：現状調査と仕様合意を行い、`plan.md` に実装可能な計画と検証方針を策定する。
* **入力**：対象チケットID（省略可）。
* **前提条件**：作業ブランチ上であること、`status: in-progress`・`phase: planning`・`phase_status: working` であること。
* **委譲ワーカー**：推奨：`worker-high`（深い現状調査・仕様検討）、`worker-low`（既存記録・コードの横断要約）。
* **手順**：
  1. 関連コード・設計書・既存ADRを調査する（深い調査や長大なログは `worker-high` 委譲や `notes/<NNN>-<slug>.md` 切り出しを活用する）。
  2. `plan.md` の合意仕様・ステップ一覧（`- [ ]`）・検証方針・判断ログを作成し、人間とすり合わせて承認を得る。
  3. 人間と次の行き先（計画レビュー実施／設計フェーズへ進行／設計をスキップして実装フェーズへ進行）を合意し、frontmatter と `## 現在地` を更新する。
* **状態更新**：合意に応じて `planning / reviewing`、`design / working`、または `implementation / working`。
* **報告形式**：合意した仕様・ステップ数・検証方針の要約、作成したノート一覧、更新後の状態と次スキル案内。

#### `aico-ticket-design`

* **目的**：合意仕様にもとづきシステム設計書・仕様書を作成または更新する。
* **入力**：対象チケットID（省略可）。
* **前提条件**：作業ブランチ上であること、`status: in-progress`・`phase: design`・`phase_status: working` であること。
* **委譲ワーカー**：推奨：`worker-high`（複雑な設計比較・設計書ドラフト）、`worker-middle`（一般設計書の更新）。
* **手順**：
  1. `plan.md` に沿って設計作業を実施し、プロジェクト資産側の設計書・仕様書を更新する（複雑な設計比較は `worker-high` を活用する）。
  2. 複数作業へ影響する重要な判断が生じた場合はADR化（`aico-create-adr`）を提案し、個別判断は `plan.md` の判断ログへ記録する。
  3. `plan.md` の該当ステップをチェックし、設計内容について人間承認を得る。
  4. 設計レビューを行うか実装へ進むかを人間と合意し、frontmatter と `## 現在地` を更新する。
* **状態更新**：合意に応じて `design / reviewing` または `implementation / working`。
* **報告形式**：更新した設計書一覧、判断ログ・ADR提案の要点、更新後の状態と次スキル案内。

#### `aico-ticket-implement`

* **目的**：`plan.md` および設計内容に沿って実装・テスト検証を完了する。
* **入力**：対象チケットID（省略可）。
* **前提条件**：作業ブランチ上であること、`status: in-progress`・`phase: implementation`・`phase_status: working` であること。
* **委譲ワーカー**：推奨：`worker-middle`（独立実装・テスト）、`worker-low`（定型実装・テスト実行・ログ抽出）、`worker-high`（難所の原因分析・バグ切り分け）。
* **手順**：
  1. `plan.md` のステップ一覧に従って実装と検証を進め、完了したステップを `- [x]` へ更新する（独立サブタスクは `worker-middle`・`worker-low` へ委譲可）。
  2. テストエビデンスや生ログを保存する必要がある場合は `artifacts/` へ格納する（導入先運用に従う）。
  3. 仕様矛盾や前提崩れを検知した場合は作業を止め、事実・選択肢・推奨案を提示して人間へエスカレーションする。
  4. ACに対する検証結果（実行環境と未確認事項を区別）を人間へ報告し、実装レビューを行うかクロージングへ進むかを合意して frontmatter と `## 現在地` を更新する。
* **状態更新**：合意に応じて `implementation / reviewing` または `closing / working`。
* **報告形式**：完了ステップ一覧、テスト・検証結果（実行環境／未確認事項）、更新後の状態と次スキル案内。

#### `aico-ticket-close`

* **目的**：変更ファイル更新・DoD確認・完了状態確定、および統合ブランチ反映後の一覧再生成を行う。
* **入力**：対象チケットID（省略可）。
* **前提条件**：
  * 作業ブランチ側：`status: in-progress`・`phase: closing`・`phase_status: working` であること（未解決のレビュー指摘が0件であること）。
  * 統合ブランチ側（マージ後実行時）：対象チケットがすでにマージされ `status: done`（または `cancelled`）であること。
* **委譲ワーカー**：推奨：`worker-low` または `worker-middle`（AC根拠・関連導線・変更差分の実物照合チェック。親セッションは人間承認と最終確定に専念）。
* **手順**：
  1. **作業ブランチ側（クロージング準備）**：
     * スクリプトで `index.md` の `## 変更ファイル` を生成・更新する。
     * ACごとの検証結果・根拠および関連記録・ADRへの導線を実物照合し、`## DoD（完了の定義）` へ記録する。未検証項目がある場合は「受け入れて完了とするか、検証を引き継ぐか」を人間へ確認し、判断結果と追跡先リンクを記録する。
     * 親チケットの場合は子チケットの結果を参照して親自身のACを確認する。
     * 人間の完了承認を得たうえで、`status: done`・`phase: closing`・`phase_status: done` へ更新してコミットし、ユーザーへ統合ブランチへの反映（push・PR/MR またはローカルマージ。PR/MR文面作成には `aico-ticket-pr` を案内）を提示する。
  2. **統合ブランチ側（マージ後の一覧再生成）**：
     * CI/CD パイプラインで自動実行していない場合、一覧・ダッシュボード再生成スクリプトを実行してコミットする。
* **状態更新**：`status: done` / `phase: closing` / `phase_status: done`。
* **報告形式**：変更ファイル数、AC別DoD判定結果、未検証項目の人間判断、統合・push/PR案内または一覧再生成結果。

#### `aico-ticket-pr`

* **目的**：作業ブランチの変更内容とチケット記録から、Pull Request / Merge Request（GitHub PR・GitLab MR の両方に対応）作成用の Title と Description を Markdown 形式で出力する。リモートへの push や PR/MR 作成操作自体は行わない。
* **入力**：対象チケットID（省略可。1.3節の入力解決ルールに従う）、比較先ブランチ（省略時は `aico-manifest.json` の `integration_branch`）。
* **前提条件**：比較先ブランチとの差分（または未マージコミット）が存在すること。
* **委譲ワーカー**：推奨：`worker-middle` または `worker-low`（比較先ブランチとの差分・記録からのPR/MR文面生成）。
* **手順**：
  1. 対象チケットが特定できた場合は、`index.md`（概要・AC・DoD・変更ファイル・関連議事録／ADR）・`plan.md`（合意仕様・検証方針・判断ログ）を読み込む（チケットに紐づかない作業ブランチの場合は、ブランチの差分とコミット履歴のみで進める）。
  2. 比較先ブランチとの `git diff`（変更ファイル一覧および主要差分）と `git log` を実物照合し、記録内容と実装差分に食い違いがないか確認する。
  3. 以下の構成で、そのまま貼り付け可能な Title と Description（Markdown）を生成して出力する。
     * **Title**：変更内容が一目で分かる簡潔な件名
     * **Description**：概要／主な変更内容／検証結果・未確認事項／関連チケット・ADR・議事録／レビュー観点（任意）
* **報告形式**：PR/MR 作成画面へそのまま転記できる Title および Description（Markdownブロック）。

#### `aico-ticket-cancel`

* **目的**：進行中または起票済みのチケットを人間の承認を得て中止し、統合ブランチ側の一覧へ反映する。
* **入力**：対象チケットID（省略可）、中止理由。
* **前提条件**：対象チケットが `active`（`open` または `in-progress`）であること。
* **手順**：
  1. **作業ブランチ側（中止確定）**：
     * 中止理由と影響（未完了成果物・子チケット・関連議事録への影響）を整理し、人間の中止承認を得る。
     * `index.md` へ中止理由を記録し、`phase`・`phase_status` は中止時点の値を維持したまま `status: cancelled` へ更新してコミットする。
     * 統合ブランチへの反映方法（記録のみ取り込むか、統合ブランチ側で直接 `cancelled` 反映するか）を人間へ確認する。
     * ※作業ブランチ作成前（`status: open`）に中止する場合は、統合ブランチ上で直接手順1〜2を完結させる。
  2. **統合ブランチ側（反映後の一覧再生成）**：
     * CI/CD パイプラインで自動実行していない場合、一覧・ダッシュボード再生成スクリプトを実行してコミットする。
* **状態更新**：`status: cancelled`（`phase`・`phase_status` は中止時点の値を維持）。
* **報告形式**：チケットID、中止時点の `phase` / `phase_status`、中止理由、後続の統合・一覧更新案内または一覧再生成結果。

#### `aico-ticket-status`

* **目的**：現在の作業・チケット状況を実物照合で把握し、中断からの再開起点と次アクションを提案する。
* **入力**：任意で対象チケットID（省略可）。
* **委譲ワーカー**：必要時：`worker-low`（大規模差分や複数記録の要約補助）。
* **手順**：
  1. `ticket_status.py`（`07`章）を実行し、`management/aico-manifest.json`・現在のGitブランチ・対象チケット（または進行中チケット候補一覧）・`plan.md` 進捗・未対応指摘件数・`git status` を実物照合で取得する。
  2. 作業ブランチ上にいる場合（または対象チケット指定時）は、必要に応じて対象チケットの `plan.md` 判断ログや統合ブランチとの `git diff` の詳細を確認する。
  3. 2.2節の対応表に従い、推奨する次スキルまたは開始起点（相談・起票・Runbook実施）を提案する。
* **報告形式**：現在ブランチ、対象チケットの3軸状態、完了済み／未完了の要点、未対応指摘件数、推奨次アクション。

### 3.4. レビュー系スキル

レビュー系スキルの適用範囲は、対象の記録構造に応じて以下のとおり使い分ける。

* **チケットおよびRunbook実施記録（`review/` 管理あり）**：4スキルすべて（`aico-review` → `aico-review-triage` → `aico-review-fix` → `aico-review-recheck`）を使用する。Runbook実施記録には `phase`・`phase_status` を設けないため、`review/findings/` の各指摘 `status` のみで進捗を管理する。
* **単一文書（Runbook手順書・ADR・議事録等、`review/` なし）**：`aico-review` 単発のみを使用する（その場で人間と採否判断・修正を行い、再確認したい場合は再度 `aico-review` を実行する）。

#### `aico-review`

* **目的**：独立コンテキストで成果物（チケットの現在フェーズ成果物、Runbook実施記録、または手順書・ADR・議事録等の単一文書）をレビューする。チケットおよびRunbook実施記録では指摘を1件1ファイルで記録して後続レビュー工程へ接続する。
* **入力**：対象チケットID・Runbook実施記録ID、または単一文書のファイルパス、対象範囲（省略時は現在フェーズの成果物および統合ブランチとの差分、または対象記録と添付物一式）。
* **前提条件**：
  * チケット対象時：作業ブランチ上であること、`status: in-progress`・`phase_status: reviewing` であること。
  * Runbook実施記録対象時：統合ブランチ上であること、対象記録が `status: in-progress` であること。
  * 単一文書（Runbook手順書・ADR・議事録等）の単発レビュー時：対象ファイルが存在すること。
* **委譲ワーカー**：必須（独立コンテキスト）：原則 `worker-middle`（重要な設計レビュー時は `worker-high`）。
* **手順**：
  1. **チケットおよびRunbook実施記録（指摘ファイル記録あり）**：
     * 現在ラウンド番号（初回は `round1`）を既存指摘から特定する（Runbook実施記録で初回時は `review/` フォルダおよび `review/index.md` を生成する）。
     * 独立コンテキストのワーカーへ、5項目委譲規約を満たす形でレビューを委譲する（親セッションの自己追認を行わないこと）。
     * 検出した各指摘をスクリプトで `review/findings/` へ作成する（`status: open`、チケット時は `<phase>-round<N>-<NNN>-<slug>.md`、Runbook実施記録時は `round<N>-<NNN>-<slug>.md`）。
     * `record_review_run.py` で `review/index.md` の初期化（Runbook実施記録で指摘0件の場合を含む）および `## レビュー実施記録`（フェーズ・ラウンド・種別・日時・比較基点・実施者・実行環境・未確認事項）の追記を行い、スクリプトで `## 指摘一覧` を再生成する。
     * チケット対象時は、指摘が1件以上あれば `phase_status: triaging` へ更新し、0件であれば人間承認のうえ次フェーズの `working`（`closing` 時は `status: done`・`closing / done`）へ進める（Runbook実施記録時は `phase_status` を更新しない）。
  2. **単一文書（Runbook手順書・ADR・議事録等）の単発レビュー時**：
     * 独立コンテキストのワーカーへ、5項目委譲規約を満たす形で対象文書のレビューを委譲する。
     * 検出した指摘・改善案・実行環境・未確認事項を人間へ報告する（`review/findings/` の作成や `phase_status` 更新は行わない）。
* **状態更新**：
  * チケット対象時：指摘あり→ `<phase> / triaging`、指摘なし→ 合意した次フェーズの `working`（`closing` 時は `status: done`・`closing / done`）。
  * Runbook実施記録対象時：指摘ファイル作成のみ（`phase_status` なし）。
  * 単一文書対象時：状態変更なし。
* **報告形式**：レビュー対象（チケット時はフェーズ・ラウンド、Runbook実施記録時はラウンド）、検出指摘件数（重要度別内訳）と要点、実行環境・未確認事項、次スキル案内（`review/` 管理対象時）。

#### `aico-review-triage`

* **目的**：未選別のレビュー指摘を人間へ提示し、採否判断を記録する（チケットおよびRunbook実施記録が対象）。
* **入力**：対象チケットIDまたはRunbook実施記録ID（省略可）。
* **前提条件**：
  * チケット対象時：作業ブランチ上であること、`status: in-progress`・`phase_status: triaging` であること。
  * Runbook実施記録対象時：統合ブランチ上であること、`review/findings/` に `status: open` の指摘が存在すること。
* **手順**：
  1. `review/findings/` から `status: open` の指摘をすべて読み込み、重要度・対象・根拠・AI推奨判断を整理して人間へ提示する。
  2. **必ず人間の判断**を受け、各指摘ファイルの `## 採否判断（人間選別）` と `status` を更新する（採用→ `in-progress`、見送り→ `cancelled`）。AIは独断で採否を決定してはならない。
  3. スクリプトで `review/index.md` の指摘一覧を再生成する。
  4. チケット対象時は、採用指摘（`in-progress`）が1件以上あれば `phase_status: fixing` へ更新し、全件見送りなら人間確認のうえ次フェーズの `working`（`closing` 時は `status: done`・`closing / done`）へ進める（Runbook実施記録時は `phase_status` を更新しない）。
* **状態更新**：
  * チケット対象時：採用あり→ `<phase> / fixing`、全件見送り→ 合意した次フェーズの `working`（`closing` 時は `status: done`・`closing / done`）。
  * Runbook実施記録対象時：各指摘の `status` 更新のみ（`phase_status` なし）。
* **報告形式**：採用件数・見送り件数、各指摘の判断一覧、次スキル案内。

#### `aico-review-fix`

* **目的**：人間が採用したレビュー指摘をすべて修正し、修正経緯を記録する（チケットおよびRunbook実施記録が対象）。
* **入力**：対象チケットIDまたはRunbook実施記録ID（省略可）。
* **前提条件**：
  * チケット対象時：作業ブランチ上であること、`status: in-progress`・`phase_status: fixing` であること。
  * Runbook実施記録対象時：統合ブランチ上であること、`review/findings/` に `status: in-progress` の指摘が存在すること。
* **委譲ワーカー**：推奨：`worker-middle`（指摘修正。定型修正は `worker-low`、難原因の修正は `worker-high`）。
* **手順**：
  1. `review/findings/` から `status: in-progress` の指摘をすべて抽出する。
  2. 各指摘に対して修正と必要なテスト検証を実施し（必要時 `worker-middle` 活用）、各指摘ファイルの `## 修正内容` に修正概要と関連コミットを記録する。
  3. すべての採用指摘への修正が完了したら人間へ報告する。チケット対象時は `phase_status: re-reviewing` へ更新する（指摘の `status` はチケット・Runbookともに独立再確認完了まで `in-progress` のまま維持する）。
* **状態更新**：
  * チケット対象時：`<phase> / re-reviewing`。
  * Runbook実施記録対象時：修正内容記録のみ（`phase_status` なし）。
* **報告形式**：修正した指摘ID一覧、関連コミット、テスト結果、次スキル（`aico-review-recheck`）の案内。

#### `aico-review-recheck`

* **目的**：独立コンテキストで指摘修正を実物照合し、解消確認または差し戻しを行う（チケットおよびRunbook実施記録が対象）。
* **入力**：対象チケットIDまたはRunbook実施記録ID（省略可）。
* **前提条件**：
  * チケット対象時：作業ブランチ上であること、`status: in-progress`・`phase_status: re-reviewing` であること。
  * Runbook実施記録対象時：統合ブランチ上であること、`review/findings/` に修正済みの `status: in-progress` 指摘が存在すること。
* **委譲ワーカー**：必須（独立コンテキスト）：原則 `worker-middle`（重要な設計レビュー時は `worker-high`）。
* **手順**：
  1. `status: in-progress` の指摘と修正差分を、独立コンテキストのワーカーへ委譲して再確認する。
  2. 各指摘ファイルの `## 独立再確認結果` に確認結果・実行環境・未確認事項を記録し、解消した指摘を `status: done` へ更新する（修正不十分な指摘は `in-progress` のまま差し戻し理由を追記する）。
  3. 再確認中に新たな問題を発見した場合は、次ラウンド（`round<N+1>`）の新規指摘ファイル（`status: open`、チケット時は `<phase>-round<N+1>-<NNN>-<slug>.md`、Runbook実施記録時は `round<N+1>-<NNN>-<slug>.md`）を作成する。同一再確認で複数件の新規指摘を作成する場合は、1件目のみ `create_review_finding.py --next-round`（または明示的に `--round <N+1>`）を指定し、2件目以降は同じ `--round <N+1>` を指定してラウンド番号の飛びを防ぐ。
  4. `record_review_run.py` で `review/index.md` の実施記録を追記し、スクリプトで指摘一覧を再生成する。
  5. チケット対象時は、新規指摘（`open`）があれば `phase_status: triaging`、差し戻し（`in-progress`）があれば `fixing` へ戻し、当該フェーズの未解決指摘が0件になれば人間承認のうえ合意した次フェーズの `working`（`closing` 時は `status: done`・`closing / done`）へ進める（Runbook実施記録時は `phase_status` を更新しない）。
* **状態更新**：
  * チケット対象時：新規指摘あり→ `<phase> / triaging`、差し戻しあり→ `<phase> / fixing`、全件確認完了→ 合意した次フェーズの `working`（`closing` 時は `status: done`・`closing / done`）。
  * Runbook実施記録対象時：解消指摘を `done`・新規指摘を `open` 作成（`phase_status` なし）。
* **報告形式**：解消件数・差し戻し件数・新規指摘件数、実行環境・未確認事項、更新後の状態と次スキル案内。

## 4. Markdown文書作成スキル仕様

管理記録の可読性と構造の一貫性を保つため、独立スキル **`aico-markdown-write`**（`.agents/skills/aico-markdown-write/SKILL.md`）を定義する。

### 4.1. 適用範囲

* 議事録・ADR・チケット配下の全記録・Runbook（手順書および実施記録）の作成・編集時に適用する。
* 導入先プロジェクト固有のシステム設計書や README 等への適用は、導入先規約（`AGENTS.md` マーカー外）に別段の定めがない限り推奨とする。

### 4.2. 規定する文書規約

`aico-markdown-write` は、以下の観点を簡潔なチェックリスト形式で定める。

| 観点 | 規約の要点 |
| :--- | :--- |
| **文字コード・改行** | UTF-8（BOMなし）・LF改行とする |
| **見出し構造** | H1は文書タイトル1つのみとし、見出しレベルを飛ばさない（`#` → `##` → `###`） |
| **文体の統一** | 管理記録・仕様・ポリシーは常体（だ・である調）で統一し、同一文書内で敬体と混在させない |
| **箇条書き・表** | 同一ファイル内で箇条書き記号（`* ` 等）を統一する。表セル内で複数項目を縦に並べる場合は `・` と `<br>` を用いる |
| **コード・図** | コードブロックには言語識別子（`text`, `json`, `python`, `mermaid` 等）を明記する。Mermaid図のラベルに括弧等を含む場合は二重引用符で囲む |
| **リンク・参照** | 管理記録間の本文リンクは標準Markdownの相対リンクを用い、frontmatter には移動に強い不変IDを用いる |
| **構成の明快さ** | 冒頭に概要を置いて全体像を先に示し、詳細は後ろの節へ配置する |
