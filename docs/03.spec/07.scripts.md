# 07. スクリプト仕様

## 概要

AIと人が共通して利用する機械処理スクリプトの実行基盤、共通規約、人用ランチャー、各スクリプトの入出力およびテスト仕様を定める。
本章では以下を定める。

* 実行環境とディレクトリ構成
* 共通規約と安全性仕様
* 人用ランチャー仕様
* 全スクリプト一覧と個別仕様
* 診断スクリプト（`doctor.py`）の検査項目
* テスト仕様

## 1. 実行環境とディレクトリ構成

### 1.1. 言語・起動方式と依存分離

* **実装言語**：Python 3.11 以上へ統一し、Windows と Linux で同一のソースコードを実行する。BAT・bash・PowerShell で業務ロジックを重複実装しないこと。
* **起動方式**：原則として `uv run <管理ルート>/scripts/<機能名>.py <引数>` を用いる。ただし `uv` への依存は起動方法のみにとどめ、`uv` がない環境でも Python 3.11 以上があれば `python3` / `py -3` 等で直接実行可能とすること。
* **標準ライブラリ原則と PEP 723**：すべての配布スクリプトは原則として Python 標準ライブラリのみで実装し、外部パッケージへ依存しない。各スクリプト冒頭には必ず以下の PEP 723 メタデータヘッダを記述する。

```python
#!/usr/bin/env python3
# /// script
# requires-python = ">=3.11"
# dependencies = []
# ///
```

* **導入先環境との非干渉**：AIco 用の `pyproject.toml`・`uv.lock`・`.venv` は導入先プロジェクトのルートへ配置しないこと。
* **外部依存を例外採用する場合の制約**：やむを得ず外部パッケージを追加する場合は、標準ライブラリで代替しない理由を AIco 本体の ADR へ記録し、当該スクリプトの PEP 723 ヘッダへ明記する（ただし `doctor.py` と `_launcher.py` はいかなる場合も標準ライブラリのみで動作すること）。

### 1.2. ディレクトリ構成と `_lib/` 設計

AIco の共有スクリプトは管理ルート配下の `scripts/` に 1 機能 1 ファイルで集約し、共通処理は `_lib/` へ分離する。スキルフォルダ（`.agents/skills/`）配下へスクリプトを分散配置してはならず、機能スクリプト同士の直接 `import` も禁止する。

```text
management/scripts/
├── _lib/                          # 共通モジュール（外部から直接実行しない）
│   ├── __init__.py
│   ├── cli.py                     # 共通引数・終了コード・UTF-8出力・--json共通スキーマ
│   ├── manifest.py                # aico-manifest.json 読込・検証・パス解決
│   ├── naming.py                  # 日時（YYYYMMDD-HHMMSS）・slug・ID検証
│   ├── frontmatter.py             # 標準ライブラリ製 YAML frontmatter 解析・出力
│   ├── validation.py              # スキーマ・3軸状態・相互参照・ブランチ更新責務検証
│   ├── markers.py                 # AICO:BEGIN / AICO:AUTO:BEGIN:<id> マーカー置換・検証
│   ├── fs.py                      # 原子的書込（一時ファイル検証→os.replace）・衝突検知
│   ├── templates.py               # management/templates/ 読込・変数展開
│   ├── git_utils.py               # 現在ブランチ取得・統合ブランチ差分取得
│   ├── markdown_links.py          # 管理記録内の相対リンク抽出・追従置換・切れ検知
│   ├── indexes.py                 # ダッシュボード・各区分一覧・指摘一覧の生成ロジック
│   └── agents_sync.py             # スキル同期・ワーカー定義生成・CLAUDE.md・ドリフト検証
├── _launcher.py                   # 人用共通ランチャー（tools/aico.* から呼出）
├── create_discussion.py           # 議事録作成
├── create_adr.py                  # ADR作成
├── create_ticket.py               # チケットフォルダ一式作成
├── create_ticket_note.py          # チケット内ノート作成
├── create_runbook.py              # Runbook手順書作成
├── create_runbook_record.py       # Runbook実施記録作成
├── create_review_finding.py       # レビュー指摘作成（チケット・Runbook両対応）
├── record_review_run.py           # レビュー実施記録の追記・review/index.md 初期化
├── update_frontmatter.py          # frontmatter・状態更新と整合検証
├── update_changed_files.py        # チケット変更ファイル一覧の自動更新
├── rebuild_indexes.py             # ダッシュボード・各一覧・指摘一覧のべき等再生成
├── ticket_status.py               # 対象チケット解決・次スキル判定・未解決指摘照会
├── archive_record.py              # 完了済み記録のアーカイブ移動と双方向リンク追従
├── sync_agents.py                 # スキル同期・ツール別ワーカー定義・CLAUDE.md 生成
├── doctor.py                      # 環境・設定・記録・同期状態の総合診断
├── init.py                        # 導入先固有設定の初期化・再設定（詳細：08章）
└── update.py                      # 版比較・配布元取得・アップデート実行委譲（詳細：08章）
```

※`init.py`・`update.py` の詳細仕様および初回導入・移行の全体仕様は `08`章を参照する。
※YAML frontmatter は AIco の規定スキーマ（フラット文字列・`null`・文字列配列）に特化した軽量パーサを `_lib/frontmatter.py` に実装し、外部ライブラリ依存を排除する。TOML 出力（Codex ワーカー定義）は生成後に標準ライブラリ `tomllib` で構文検証してから書き込む。

## 2. 共通規約と安全性仕様

### 2.1. 共通オプションと引数規約

日次運用の全15機能スクリプトは非対話（標準入力待ちをしない）で動作し、必要な値はすべてコマンドライン引数で受け取る（設定ウィザードを兼ねる `init.py` のみ、引数省略＋TTY接続時の対話モードと引数指定／非TTY時の非対話モードを両対応とする）。

| オプション | 対象 | 役割 |
| :--- | :--- | :--- |
| `--dry-run` | 書き込み・移動を伴う全スクリプト | 実ファイルを一切変更せず、作成・更新・移動予定と差分要約のみを出力する |
| `--root <path>` | 全スクリプト（任意） | リポジトリルートを明示指定する（省略時はカレントディレクトリから上位へ `aico-manifest.json` を探索して特定する） |
| `--json` | 全機能スクリプト（任意） | 人向けテキストの代わりに機械可読な JSON を標準出力へ出力する |
| `--allow-non-integration` | 統合ブランチ専用の作成・一覧再生成系（任意） | CI の detached HEAD や人間承認済みの例外ケースで統合ブランチガードを明示解除する |
| `--help` / `-h` | 全スクリプト | 用途・引数・終了コードのヘルプを表示して終了コード `0` で終了する |

* **既定モード**：`--dry-run` 未指定時は書き込みを実行する。
* **`--json` 共通出力スキーマ**：全機能スクリプトの JSON 出力は `_lib/cli.py` で共通トップレベルキー（`status`: `"ok" | "error"`、`id`: 対象IDまたは `null`、`path`: 主対象パスまたは `null`、`changed_files`: 変更［予定］パス配列、`warnings`: 警告配列、`errors`: エラー配列、`data`: スクリプト固有詳細オブジェクト）へ統一する。
* **パス表記の正規化**：出力および Markdown リンク内のパス区切りは OS によらず常にスラッシュ（`/`）へ正規化する。

### 2.2. 終了コードと出力規約

すべての機能スクリプトは、以下の終了コードと出力ルールに統一する。

| 終了コード | 意味 | 想定ケース |
| :--- | :--- | :--- |
| **`0`** | 成功 | 処理完了、`--dry-run` 正常終了、`doctor.py` で ERROR なし（`--strict` 時は WARN もなし） |
| **`1`** | 検査・処理の失敗 | ファイル衝突、frontmatter 規約違反、不正な状態遷移、ブランチ責務違反、マーカー不整合、Git 差分取得失敗、`sync_agents.py --check` ドリフト検知、`doctor.py` で ERROR 検知 |
| **`2`** | 引数の誤り | 必須引数不足、不正なオプション、不正な `slug` 形式（`argparse` 準拠） |

※Linux（POSIX）では終了コードの上限が `255` であり、`126`〜`255` は実行不可・コマンド未検出・シグナル終了の予約領域となるため、AIco の機能スクリプトはクロスプラットフォームで安全に使える `0`・`1`・`2` のみを使用する。

* **標準出力と標準エラー出力の分離**：正常結果・変更予定・診断結果（`OK` / `WARN` / `ERROR` の構造化結果）は `stdout` へ、引数エラーや致命的な実行失敗メッセージは `stderr` へ出力する。
* **文字コードと決定性**：入出力はすべて UTF-8（BOM なし）・LF 改行とする。Windows 環境でも文字化けしないよう起動時に標準入出力の UTF-8 エンコーディングを強制設定する。一覧やログの出力順はソート規則に従って常に決定的とする。
* **検査回避の禁止**：スクリプトの検査で終了コード `1` となった場合、AI は手作業でファイルを直接書き換えて検査を迂回してはならない。原因を確認し、条件を整えたうえでスクリプトを再実行すること。

### 2.3. 原子的更新・べき等性・セキュリティ

* **原子的更新（Atomic Write）**：既存ファイルの書き換えは、完成した全文をメモリ上で生成・構文検証した後、同一ディレクトリ内の一時ファイルへ書き込み、`os.replace()` で置換する。複数ファイルを連動更新する場合（双方向ID追記・アーカイブ移動・ADR置換等）は、すべての事前検証を完了してから書き込むことで不整合を防ぐ。
* **衝突時の安全停止**：新規作成先パスが既に存在する場合は自動連番（`-2` 等）や上書きを行わず、終了コード `1` で停止する。
* **ブランチ更新責務ガード**：`04`章のブランチ別更新責務に従い、統合ブランチ専用の記録作成・全体一覧再生成・アーカイブ移動は現在ブランチが `aico-manifest.json` の `integration_branch` であることを事前検証する（作業ブランチ上での誤実行による競合を防止する）。
* **べき等性**：`rebuild_indexes.py`・`update_changed_files.py`・`sync_agents.py` は同一状態で再実行したときに差分が発生してはならない。自動生成ブロック（`AICO:AUTO`）内には実行時刻を出力せず、内容に変更がないファイルは書き換えをスキップする。
* **破壊操作の抑止**：スクリプトは自動 `git commit`・自動 `git push`・履歴改変を一切行わない。削除や移動（`archive_record.py`・`sync_agents.py` の同期先削除）は事前検証を行い、Git によりいつでも復旧可能な状態を保つ。
* **秘密情報の保護**：トークン・パスワード・個人情報等の秘密情報をスクリプトの引数・標準出力・生成記録・ログへ出力してはならない。

## 3. 人用ランチャー仕様

AI は `uv run <管理ルート>/scripts/<機能名>.py` を直接呼び出し、人間は `tools/aico.sh`（Linux）または `tools/aico.bat`（Windows）を経由して同じスクリプト実体を利用する。

### 3.1. 薄いラッパー（`tools/aico.sh`・`tools/aico.bat`）

OS 別ラッパーには業務ロジックや JSON 解析・ディレクトリ探索ロジックを持たせず、以下の4責務のみを担う。

1. **実行ランタイムの解決**：`uv` が利用可能であれば `uv run` を優先使用し、`uv` がない場合は利用可能な Python 3.11 以上（Linux：`python3` → `python`、Windows：`py -3` → `python`）へフォールバックする。いずれも見つからない場合はインストール案内を `stderr` へ出力し、終了コード `1` で終了する。
2. **UTF-8 環境の強制**：`PYTHONUTF8=1`（および `PYTHONIOENCODING=utf-8`）を設定して起動する。
3. **引数の安全な転送**：環境変数 `AICO_MANAGEMENT_ROOT`（未設定時は導入時に設定された既定値 `management`）配下の `scripts/_launcher.py` を対象とし、空白や日本語を含むパス・引数が分割されないよう適切にクォートして転送する。
4. **終了コードの透過伝達**：`_launcher.py`（および呼び出された機能スクリプト）の終了コードをそのまま呼び出し元シェルへ返す。

※上位ディレクトリの探索や `aico-manifest.json` の読み込みによる管理ルート解決はすべて `_launcher.py` / `_lib/manifest.py` 側へ集約し、OS 間の二重実装を防ぐ。
※Windows の `tools/aico.bat` では、アップデート実行中に `tools/aico.bat` 自体が差し替えられても `cmd.exe` の逐次読み込みで異常終了しないよう、ランチャー起動から `exit /b` までを丸括弧ブロック `(...)` で囲んで事前一括パースを保証する。

### 3.2. 共通ランチャー（`management/scripts/_launcher.py`）

* **直接実行モード（引数あり）**：`tools/aico.sh <機能名> [引数...]` の形式で指定された場合（例：`tools/aico.sh doctor`、`tools/aico.sh rebuild_indexes --dry-run`、`.py` 拡張子有無いずれも許容）、対応する機能スクリプトをサブプロセス実行し、終了コードをそのまま返す。
* **対話案内モード（引数なし＋TTY接続時）**：利用可能な機能スクリプト一覧を番号付きメニューで表示し、番号選択後に `--help`（使い方）を確認したうえで引数を入力して実行できる。
* **非対話環境（引数なし＋非TTY時）**：パイプ接続や CI など端末へ接続されていない環境では入力待ちを行わず、「引数未指定のため一覧表示のみ行った」旨の案内と機能一覧・使い方を `stdout` へ出力して終了コード `0` で終了する（機密漏洩および `--json` 出力破損防止のため、通常時の引数ダンプは行わない）。

### 4.2. 記録作成スクリプト

すべての作成スクリプトは、以下の共通ルールに従う。

* `slug` 形式（`^[a-z0-9]+(?:-[a-z0-9]+)*$`）と衝突チェックを事前実行し、`management/templates/` からテンプレートを展開して `created`・`updated` に現在ローカル日時（`YYYY-MM-DD HH:MM:SS`）を自動設定する。
* 空ディレクトリ（`notes/`・`review/findings/`・`records/`）には `.gitkeep` を配置せず、初回ファイル作成時に親ディレクトリをオンデマンド生成する。
* 相互参照IDを引数で指定された場合は対象記録の実在を検証し（不存在時は終了コード `1`）、双方向ID配列（`parent`↔`children`、`discussions`↔`tickets`、`adrs`↔`tickets`、`followups`）を同一処理で自動追記する。
* 統合ブランチ専用の作成スクリプト（`create_discussion.py`, `create_adr.py`, `create_ticket.py`, `create_runbook.py`, `create_runbook_record.py`）は、現在ブランチが `integration_branch` でない場合に終了コード `1` で拒否する（人間承認済みの例外や CI 用に `--allow-non-integration` を用意）。

個別仕様は以下のとおりとする。

* **`create_discussion.py`**
  * **主な引数**：`--slug <slug>`（必須）、`--title <件名>`（必須）、`--status <open|in-progress>`（既定 `open`）、`--followup-from <Runbook実施記録IDまたはパス>`（任意。指定時は Runbook 実施記録の `followups` へ自動追記）。
  * **生成物**：`management/02.discussions/<YYYYMMDD-HHMMSS>-discussion-<slug>.md`。
* **`create_adr.py`**
  * **主な引数**：`--slug <slug>`（必須）、`--title <件名>`（必須）、`--status <open|accepted>`（既定 `open`）、`--ticket <id>`（任意・複数可。チケット側 `adrs` へ双方向追記）、`--discussion <id>`（任意・複数可。議事録側 `adrs` へ双方向追記）、`--supersedes <旧ADR ID>`（任意）。
  * **生成物**：`management/03.adr/<YYYYMMDD-HHMMSS>-adr-<slug>.md`。
  * **承認フロー整合**：`--supersedes` は `--status accepted` 指定時のみ許可し、旧 ADR を `status: deprecated`＋`superseded_by` へ同時更新する（`--status open` で `--supersedes` が指定された場合は未承認ドラフトによる現行 ADR 廃止を防ぐため終了コード `1` で拒否する。承認後に置換する場合は `update_frontmatter.py --supersedes` を用いる）。
* **`create_ticket.py`**
  * **主な引数**：`--slug <slug>`（必須）、`--title <件名>`（必須）、`--branch <ブランチ名>`（任意。省略時は `feature/<チケットID>`、`{id}`・`{slug}` プレースホルダ展開に対応。例：`--branch "feat/{id}"`）、`--parent <親チケットID>`（任意。親の `children` へ双方向追記）、`--discussion <id>`（任意・複数可。議事録側 `tickets` へ双方向追記）、`--adr <id>`（任意・複数可。ADR 側 `tickets` へ双方向追記）、`--followup-from <Runbook実施記録IDまたはパス>`（任意。`followups` へ追記）。
  * **生成物**：`management/04.tickets/<YYYYMMDD-HHMMSS>-ticket-<slug>/` 配下に `index.md`（`status: open`・`phase: drafting`・`phase_status: working`）・`plan.md`・`review/index.md` を生成する（`notes/`・`review/findings/` は初回作成時にオンデマンド生成）。
* **`create_ticket_note.py`**
  * **主な引数**：`--ticket <チケットIDまたはパス>`（必須）、`--slug <slug>`（必須）、`--title <件名>`（必須）。
  * **生成物**：`<チケットフォルダ>/notes/<NNN>-<slug>.md`（`id`/`title`/`created`/`updated` のみ、`status` なし。`NNN` は既存ノートの最大番号 + 1 を 3 桁 0 埋めで採番、初回 `001`）。
* **`create_runbook.py`**
  * **主な引数**：`--slug <slug>`（必須）、`--title <件名>`（必須）。
  * **生成物**：`management/05.runbooks/<slug>/runbook.md`（`id`/`title`/`created`/`updated` のみ、`status` なし。`records/` は初回実施記録作成時にオンデマンド生成）。
* **`create_runbook_record.py`**
  * **主な引数**：`--runbook <Runbook slug>`（必須）、`--slug <実施記録slug>`（必須）、`--title <件名>`（必須）。
  * **生成物**：`management/05.runbooks/<runbook>/records/<YYYYMMDD-HHMMSS>-<slug>/index.md`（`status: in-progress`、`runbook: <runbook>`）。対象 `runbook.md` が存在しない場合は終了コード `1` で停止する。
* **`create_review_finding.py`**
  * **主な引数**：`--target <チケットID・パス または Runbook実施記録パス>`（必須）、`--slug <slug>`（必須）、`--title <件名>`（必須）、`--severity <critical|major|minor>`（必須）、`--reviewer <実施者>`（必須）、`--phase <phase>`（チケット時は任意：省略時は対象チケットの現在 `phase` を自動参照、Runbook実施記録時は指定不可）、`--round <N>`（任意。省略時はチケットの対象フェーズ内／Runbook実施記録内の現行最大ラウンドを自動判定し、初回は `1`）、`--next-round`（任意。`aico-review-recheck` で新規問題を発見した際に現行最大ラウンド + 1 を自動採番する。`--round` と排他）。
  * **生成物**：
    * チケット時：`<チケット>/review/findings/<phase>-round<N>-<NNN>-<slug>.md`（`status: open`、`NNN` は同一フェーズ・同一ラウンド内で `001` から採番）。
    * Runbook実施記録時：`<Runbook実施記録>/review/findings/round<N>-<NNN>-<slug>.md`（初回時は `review/index.md` も自動生成）。

### 4.3. 状態・記録・一覧更新スクリプト

* **`record_review_run.py`**
  * **目的**：`review/index.md` の初期化（Runbook 実施記録で初回レビュー指摘 0 件だった場合を含む）と、`## レビュー実施記録` への定型履歴追記を行う。
  * **主な引数**：`--target <チケットID・パス または Runbook実施記録パス>`（必須）、`--kind <initial|recheck>`（必須）、`--reviewer <実施者>`（必須）、`--base-commit <比較基点>`（必須）、`--env <実行環境>`（必須）、`--unverified <未確認事項>`（任意。既定 `なし`）、`--phase <phase>`（チケット時は任意：省略時は現在 `phase` 自動参照、Runbook 時は指定不可）、`--round <N>` または `--next-round`（任意。省略時は対象内の現行ラウンド自動判定）。
  * **動作仕様**：`review/index.md` が未存在ならテンプレートから生成したうえで、`## レビュー実施記録` 末尾へフェーズ（チケット時）・ラウンド・種別・ローカル日時・比較基点・実施者・実行環境・未確認事項を定型追記する。
* **`update_frontmatter.py`**
  * **目的**：対象記録の YAML frontmatter をスキーマ・遷移整合検証付きで更新し、`updated` 日時を自動反映する。
  * **主な引数**：`--file <対象Markdownパス>`（必須）、`--set <key=value>`（複数可）、`--set-null <key>`（`null` 許容キーのクリア・複数可）、`--add <list_key=value>`（配列へ重複なしで追記・複数可）、`--remove <list_key=value>`（配列から削除・複数可）、`--supersedes <旧ADR ID>`（任意。ADR を `status: accepted` へ確定する際に旧 ADR の `status: deprecated`＋`superseded_by` を同一処理で更新）、`--force`（任意。手戻り・フェーズスキップなど通常遷移外の状態補正を人間承認前提で許可）。
  * **検証ルール**：
    * **不変・未知キー拒否**：`id`・`created` の変更、および記録種別スキーマ外の未知キー（例：レビュー指摘へ `phase` を設定、Runbook手順書へ `status` を設定）は `--force` 指定時も常に終了コード `1` で拒否する。
    * **許容3軸組み合わせ（チケット）**：`status: open` は `drafting / working` のみ、`status: done` は `closing / done` のみ、`status: in-progress` は `phase_status != done` のみ許可し、不正組み合わせは `--force` 指定時も常に拒否する（`status: cancelled` は中止時点の `phase`・`phase_status` を維持）。
    * **完了時の未解決指摘ガード**：チケットを `status: done` へ更新する際、`review/findings/` に未解決指摘（`open` または `in-progress`）が残っている場合は終了コード `1` で拒否する。
* **`update_changed_files.py`**
  * **目的**：チケット `index.md` の `<!-- AICO:AUTO:BEGIN:changed-files -->` 〜 `<!-- AICO:AUTO:END:changed-files -->` を、統合ブランチとの Git 差分から生成・更新する。
  * **主な引数**：`--ticket <チケットIDまたはパス>`（任意。省略時は現在ブランチと一致するチケットを自動特定）、`--base <比較基点ブランチ>`（任意。省略時は `aico-manifest.json` の `integration_branch`）。
  * **動作仕様**：`git diff --name-status <base>...HEAD` を取得し、`aico-manifest.json` の `management_root` 配下を除いたプロジェクト資産の変更一覧をパス昇順で出力する。Rename（`R100 old new` 等）は種別 `R`・パス `old -> new` へ正規化し、プロジェクト資産の変更が 0 件のときは `変更されたプロジェクト資産はありません。` を出力する。作業ツリーに未コミット変更が残っている場合は `WARN` を出力して注意喚起する。
* **`rebuild_indexes.py`**
  * **目的**：管理ルート配下の自動生成ブロック（`<!-- AICO:AUTO:BEGIN:<id> -->` 〜 `<!-- AICO:AUTO:END:<id> -->`）を実記録からべき等に再生成する。CI/CD パイプラインからの非対話実行にも対応する。
  * **主な引数**：`--scope <all|dashboard|discussions|adr|tickets|runbooks|reviews>`（既定 `all`）、`--target <特定チケットまたはRunbook実施記録パス>`（`--scope reviews` 時に対象を絞る場合）、`--allow-non-integration`（任意）。
  * **ブランチガード**：現在ブランチが `integration_branch` でない場合、`--scope reviews --target <対象>` 以外の実行は終了コード `1` で拒否する（作業ブランチ上での全体一覧誤更新を防止）。
  * **生成規則**：`02`章第4節のマーカー `<id>`・列構成・ソート規則（レビュー指摘はフェーズ工程順・ラウンド数値昇順）に従い、空値は `-` と表示し、`archived/` 配下は除外する。

### 4.4. 照会・運用・同期スクリプト

* **`ticket_status.py`**
  * **目的**：読み取り専用で対象チケットを特定し、3軸状態・推奨次スキル・進捗・未解決指摘を一括照会する（全スキルの1.3節入力解決および2.2節決定表の共通実装）。
  * **主な引数**：`--ticket <チケットIDまたはパス>`（任意。省略時は現在 Git ブランチ名と `04.tickets/*/index.md` の `branch` 属性を照合して自動特定）、`--json`（任意）。
  * **出力内容**：現在ブランチ、`git status` 要約、特定チケットの3軸状態（不整合検知含む）、`06`章2.2節の決定表に基づく推奨次スキル、`plan.md` のチェックリスト進捗（完了数／総数）、`review/findings/` の状態別件数および未解決（`open` / `in-progress`）指摘一覧。自動特定できない場合は進行中（`active`）チケット候補一覧を出力する。
* **`archive_record.py`**
  * **目的**：完了済み記録を各区分の `archived/` へ移動し、管理ルート配下の被参照リンクと移動対象自身の内部相対リンクを双方追従更新したうえで一覧を再生成する。
  * **主な引数**：`--target <記録IDまたはパス>`（必須）。
  * **事前検査**：
    * 統合ブランチ上であること（作業ブランチ上は終了コード `1` で拒否）。
    * 既に `archived/` 配下でないこと、移動先パスに衝突がないこと。
    * 種別ごとのアーカイブ可否基準を満たすこと：
      * 議事録・チケット・Runbook実施記録：`status` が `done` または `cancelled` であること。
      * ADR：`status` が `deprecated` または `cancelled` のみ許可（現行採用中の `accepted` および `open` は拒否）。
      * Runbook手順書：配下の `records/` に `status: in-progress` の実施記録が残っていないこと。
  * **処理手順**：`--dry-run` では移動元・移動先・書き換え対象となる外部および内部のリンク件数を一覧表示する。本実行では移動 → 管理ルート配下からの被参照相対リンク置換 → **移動対象自身（フォルダ配下の全 Markdown を含む）の内部から外部へ向かう相対リンクの階層補正** → `_lib/indexes.py` による一覧再生成を一貫実行する。
* **`sync_agents.py`**
  * **目的**：`05`章で定めたスキル同期・ツール別ワーカー定義生成・`CLAUDE.md` 生成を実行する。
  * **主な引数**：`--only <all|skills|workers|context>`（既定 `all`）、`--check`（任意。ファイルを書き換えず、同期ドリフトがあれば終了コード `1` で終了する検証モード。`--dry-run` は変更予定を表示し正常時は終了コード `0`）。
  * **動作仕様**：
    1. `aico-manifest.json` の `tools` を読み込み、`claude` 有効時は `.claude/skills/`、`copilot` 有効時は `.github/skills/` へ `.agents/skills/` の全スキル（`aico-*` および導入先固有スキル）をミラー同期する（原本側削除も追従）。
    2. `management/templates/workers/worker-{high,middle,low}.md` と `aico-manifest.json` の `worker_models` から、`tools` で有効化されたツールの `worker-{high,middle,low}.*` 定義ファイルを生成する。各ツール `agents/` 配下の導入先独自サブエージェント定義は削除・上書きしない。`model` または `effort` が空文字 `""` の項目はキーを省略またはコメント出力し、Codex の `.toml` は `tomllib` で構文検証してから書き込む。
    3. `tools` に `claude` が含まれる場合、ルート直下の `CLAUDE.md`（`@AGENTS.md` 1行のみ）を生成・同期する。

## 5. 診断スクリプト（`doctor.py`）の検査項目

`doctor.py` は読み取り専用・標準ライブラリのみで導入先環境の整合性を一括検査し、項目ごとに `OK` / `WARN` / `ERROR` と推奨修復コマンドを出力する。

* **主な引数**：`--strict`（`WARN` が 1 件以上ある場合も終了コード `1` とする）、`--json`（構造化出力）。

| 検査カテゴリ | 検査内容 | 判定基準 | 推奨修復手段 |
| :--- | :--- | :--- | :--- |
| **実行環境** | Python 3.11 以上・`uv`・`git` の存在と UTF-8 出力可否 | Python 3.11 未満または `git` なし：`ERROR`<br>`uv` なし：`WARN`（Python 直接実行は可） | Python / `uv` の導入案内 |
| **マニフェスト・ワーカー設定** | `aico-manifest.json` の JSON 妥当性、必須キー、`source_repository` の型妥当性、`tools` 許容値、`integration_branch` の Git 実在、`worker_models` の `model`/`effort` 両キー存在および空文字有無 | 欠損・不正値・ブランチ不存在：`ERROR`<br>有効ツールの `model` / `effort` 空文字：`WARN` | マニフェスト修復、`tools/aico.sh init` または `worker_models` 記入＋`sync_agents.py` 案内 |
| **コンテキスト・配置構造** | `AGENTS.md` 存在、`claude` 有効時の `CLAUDE.md`（`@AGENTS.md` 1行のみ）一致、重複禁止ファイル（`GEMINI.md`・`.github/copilot-instructions.md`）有無、管理ルート直下 `archived/` 禁止、`.agents/skills/` 配下へのスクリプト混入禁止 | 必須ファイル欠損・構造違反：`ERROR`<br>重複禁止ファイル存在：`WARN` | `sync_agents.py` 実行・不要ファイル整理案内 |
| **スキル・ワーカー同期** | `.agents/skills/` と各同期先の一致、`SKILL.md` の UTF-8/LF・フォルダ名と `name` 一致・`description` 必須、ワーカー定義ファイルとマニフェストの一致 | 差分・未同期・書式違反：`ERROR` | `sync_agents.py` 実行・`SKILL.md` 修正案内 |
| **マーカー整合** | `AGENTS.md` の `AICO:BEGIN`/`END`、各一覧ファイルおよび各チケット `index.md`（`changed-files`）の `AICO:AUTO:BEGIN:<id>`/`END:<id>` の対称性・入れ子・同一 `<id>` 重複有無 | 片側欠損・逆転・入れ子・重複：`ERROR` | マーカー修復または `rebuild_indexes.py` 実行案内 |
| **記録・frontmatter・状態・相互参照** | 文字コード（UTF-8 BOM なし）・LF 改行、`02`章の2軸区分に従った必須 frontmatter、`id`/パス一致、`slug`/`title`/日時書式、レビュー指摘の `phase`/`round` 重複禁止・`reviewer` 必須、3軸状態整合、`done` チケットの未解決指摘残存、`active` チケット間の `branch` 重複、相互参照IDの実在・双方向一致 | 規約違反・不整合：`ERROR` | 該当ファイルと違反項目の修正案内 |
| **一覧鮮度・リンク・Markdown構造** | 各 `index.md` の期待生成内容との鮮度ドリフト（統合ブランチ時は全体、作業ブランチ時は対象チケットの `review/index.md`）、管理ルート配下の相対リンク切れ、軽量 Markdown 構造（H1 重複・見出しレベル飛び・コードブロック言語指定漏れ） | 相対リンク切れ：`ERROR`<br>一覧鮮度ドリフト・Markdown 構造不備：`WARN` | `rebuild_indexes.py` 実行・リンク／Markdown 修正案内 |

## 6. テスト仕様

### 6.1. テストの配置と方針

* **配布物からの分離**：テストコードは AIco リポジトリ本体の `tests/`（配布テンプレートの外）へ配置し、導入先プロジェクトへは配布しない。
* **テストの2層構成**：
  * **単体テスト（Unit）**：`_lib/` の各モジュール（`naming`, `frontmatter`, `validation`, `markers`, `fs`, `markdown_links`, `indexes`, `agents_sync` 等）の正常系・境界値・異常系を高速検証する。
  * **結合テスト（CLI / E2E）**：一時ディレクトリに模擬リポジトリ（`git init` 含む）を構築し、全15機能スクリプトおよび `tools/aico.sh` / `tools/aico.bat` をサブプロセスとして実起動し、終了コード・標準出力（`--json` 含む）・生成ファイルを検証する。

### 6.2. 必須検証項目

リリース前（および CI 実行時）に、以下の観点を自動テストまたは実機検証で確認する。未確認の OS・環境がある場合はリリースノートへ必ず明記すること。

| 検証領域 | 必須テストケース |
| :--- | :--- |
| **基本動作と終了コード** | 全15機能スクリプトの正常終了（`0`）、検査・衝突・不正状態・ブランチ違反エラー（`1`）、引数誤り（`2`）、および `--json` 共通スキーマの妥当性 |
| **`--dry-run` とべき等性** | `--dry-run` 実行前後でファイル内容・タイムスタンプが一切変化しないこと。`rebuild_indexes.py`・`update_changed_files.py`・`sync_agents.py` の連続2回実行で2回目に差分が発生しないこと |
| **衝突・原子的更新・ガード** | 同名記録の重複作成で上書きせず終了コード `1` となること。書き込み途中で例外発生時に元ファイルが破損しないこと。作業ブランチ上で統合ブランチ専用スクリプトや `rebuild_indexes.py --scope all` が拒否され、`--allow-non-integration` で解除できること。未承認 ADR での `--supersedes` と未解決指摘残存での `status: done` が拒否されること |
| **レビュー・照会・アーカイブ** | チケットおよび Runbook 実施記録の双方で `create_review_finding.py`（`--next-round`・`reviewer` 必須含む）・`record_review_run.py`（Runbook 指摘0件時の初期化含む）・`ticket_status.py` が正しく動作すること。`archive_record.py` で被参照リンクと移動対象自身の内部相対リンクが双方正しく追従され、ADR の `accepted` や `active` 記録のアーカイブが拒否されること |
| **同期・マーカー・診断** | `sync_agents.py` で全スキル同期・`worker-{high,middle,low}` 生成（導入先独自エージェント保持）・`CLAUDE.md` 同期・`--check` 終了コード `1` が機能すること。一意ラベルマーカーの複数配置・重複検知、`doctor.py` の全7カテゴリ検査（`--strict` 含む）が正しく動作すること |
| **クロスプラットフォーム** | Windows と Linux の双方で、空白・日本語を含むリポジトリパス、引数転送、終了コード伝達、UTF-8 出力、`uv` なし環境での Python 直接フォールバック起動、非 TTY 時の `_launcher.py` 非停止動作を確認すること |
